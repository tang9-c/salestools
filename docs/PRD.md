# 目标客户体检与联系人管理 MCP 产品需求文档

状态：截至 2026-10-01 的产品功能与验收基线。共享联系人库已在本地 `main` 实现，默认关闭；联系人上传页面及生产解析沙箱已在 `codex/contact-upload-mcp-app-20260929` 分支实现并通过远程 CI，尚未合并 `main`。本文区分已实现能力与实际验收，不表示功能已经在线启用、发布或部署。操作说明见 [快速入门](QUICKSTART.md)及[联系人管理 skill](../skills/salestools-contact-management/SKILL.md)，字段定义见[联系人数据契约](superpowers/specs/contact-data-contract.md)。

## 1. 产品目标与用户

面向通过 MCP 客户端工作的 B2B 销售人员：先用企业名称了解基本情况；确认法定主体后，可追问具体问题，也可按需生成有来源依据的中文销售评估报告。找人时可以搜索公开网页的关键岗位人员；启用共享联系人库后，还可从简历、名片建立人物、组织及项目档案，按公司、学校、技能或项目客户检索，并逐步核实与维护资料。产品帮助销售选择值得访谈的方向，不预测成交概率，也不把招聘或融资直接视作采购意向。

当前交付形态是远程 MCP 服务，客户端通过 HTTPS `/mcp` 访问。已开发专用于联系人文件导入的 MCP App／外部网页入口；它不是完整联系人管理后台。ChatGPT 内嵌 App、Codex 外部页面及手机拍照的真实宿主兼容性仍待验收。Zoho CRM 只读联系人来源已完成本地接入，真实 CRM、远程 CI 与宿主大响应仍待验收；当前没有飞书集成。

## 2. 用户流程

1. 用户说“了解这家公司”或意图不明确时，调用 `get_company_profile`。返回候选法定主体及可获得的基础画像；多候选时由用户确认，不自动选择。
2. 综合找人时，先用 `search_contacts` 查共享库；有招聘目标公司时再用 `discover_contacts` 查公开岗位线索；对库内候选用 `get_contact` 核对档案和证据。用户可只执行其中一个环节。公司、学校或项目客户关键词可显式包含待核实线索；结果必须标明正式记录、待核实线索或公开网页线索，查询不自动触发导入、合并或其他写入。
3. 导入简历或名片有两条路径：上传页面通过 `open_contact_upload` 打开，用户选择文件、等待完整预览并点击确认；有授权的本地文件环境可通过鉴权的 `/contact-files` 或 `contacts:upload` CLI 上传，再用 `import_contacts` 抽取。支持 PDF/JPG/JPEG/PNG，单文件最多 20 MB，PDF 最多 50 页。聊天／CLI 路径在用户明确授权导入且主体唯一时可用 `auto_create:true` 提交，无需逐字段、逐关系选择；页面路径必须由用户点击确认。具体提交与阻断规则见第 4.3 节。
4. 用户已确认法定名称与 18 位统一社会信用代码，并想了解特定问题时，调用 `ask_company`；无需先生成正式报告。它同步返回带引用的回答或明确的证据不足、失败状态，不改写已有报告。
5. 用户明确要求正式评估后，调用 `submit_assessment`。评估执行时需要能读取到匹配且未过期的主体画像；如果没有，任务会失败并提示主体信息不可用。任务异步处理；重复主体优先复用进行中任务或 30 天内已完成报告。
6. 使用 `assessment_id` 调用 `get_assessment_status`，状态为 `processing`、`completed` 或 `failed`。完成后调用 `get_assessment_report` 阅读 Markdown 报告；处理中或失败时返回状态消息。

新任务返回 `estimated_minutes: "5-40"`，只是经验区间，不含排队时间，也不是完成时限承诺。`force_refresh=true` 跳过已完成报告缓存，但仍复用同一主体的进行中任务。

## 3. MCP 工具

| 工具 | 关键输入 | 当前输出与边界 |
| --- | --- | --- |
| `get_company_profile` | `query`，可选 `region_hint` | `candidates`、`basic_profile`、`source_status`、`cache_hit`；只用企查查，唯一且名称匹配的主体才补充基础画像；上游不可用时明确失败。 |
| `discover_contacts` | `query`，可选 `region_hint`、`source=web/zoho/all`、`zoho_accounts`、`zoho_account_records` | 默认网页结果维持最多 3 家、每家 10 名当前联系人及 10 条历史证据；Zoho 独立区域实时返回已选 CRM 客户的全部已取得关联联系人、两类负责人、候选、连接状态与完整性，不受网页人数上限约束。 |
| `submit_assessment` | `legal_name`、`credit_code`，可选 `force_refresh` | 新建或复用任务，返回 `assessment_id`、`status`、`cache_hit`；新任务附预计时间，缓存命中附 `cached_at`。 |
| `get_assessment_status` | `assessment_id` | 返回三态及简短进度或失败消息。 |
| `get_assessment_report` | `assessment_id` | 完成时返回 Markdown、综合机会、推荐产品、采集时间、动态信号新鲜度与来源状态；其他状态只返回状态消息。 |
| `ask_company` | `legal_name`、`credit_code`、`question`，可选 `assessment_id` | 对已确认主体同步追问；返回 `answered/insufficient/failed`、Markdown、是否补查、采集时间与实际引用来源；不修改七产品评估。 |

上述六个基础工具保持可用。启用 `CONTACT_GRAPH_ENABLED=true` 并配置独立图谱数据库和 Rust 可执行文件后，服务注册以下共享联系人库工具：

| 工具 | 当前行为与边界 |
| --- | --- |
| `open_contact_upload` | 上传功能分支新增的用户入口；返回内嵌上传 App 与短时外部链接。支持选择 PDF／图片，手机相机能力取决于真实宿主。`create_contact_upload_session` 仅供 App 调用，不作为聊天操作入口。 |
| `import_contacts`、`get_contact_import`、`commit_contact_import`、`cancel_contact_import` | 依据已上传的 `file_id` 异步抽取、分页预览、自动创建或人工选择提交、取消；抽取不等于入库。导入状态为 `queued/processing/ready_for_review/committed/failed/cancelled`。 |
| `import_contacts_text` | 输入 `text` 和稳定的 `operation_id`，直接从文字生成导入候选并返回 `import_id`；复用上述预览、确认提交与取消工具，不上传文件、不调用 Docling、不直接入库。 |
| `search_contacts`、`get_contact` | 按姓名、组织、职位、技能或关键词检索，分页读取档案、证据、冲突、关系和待核实线索；支持沿人物参与项目、项目服务客户的路径按客户名找人。语义/混合检索需要嵌入端点，可用性不足时退回关键词并给出警告。 |
| `save_contact`、`merge_contacts`、`delete_contact` | 创建、版本化编辑、明确恢复或归档人物、组织及项目；人工合并仅限人物。删除为归档，不是清除历史证据。 |
| `save_contact_relation`、`delete_contact_relation` | 保存或归档有依据的任职、组织及人物关系；每段任职可独立保留职位和时间。 |
| `review_contact_claim` | 确认或拒绝待核实线索。确认需当前实体版本、稳定操作 ID 和 1–500 字符审核说明；必要时补正确目标或更正值，形成手工审核证据。 |
| `ask_contacts` | 依据库内实体、关系及短证据回答人物关系和任职问题；返回 `answered/clarify/insufficient/failed`，同名或证据不足时不猜测。 |
| `retry_contact_index` | 仅在嵌入服务已配置时，重试失败的联系人向量索引。 |

写入操作使用稳定 `operation_id` 安全重试，修改和合并需当前版本；合并目标及字段取舍必须明确选择。导入提交携带 `preview_version`，操作 ID 固定为 `contact-import:<import_id>`；响应丢失时原样重试，不更换 ID 盲目重放。工具的准确参数和结果以 [联系人 MCP 注册](../src/mcp/contact-tools.ts)、[导入工具](../src/mcp/contact-import-tools.ts)、[检索工具](../src/mcp/contact-search-tools.ts)、[问答工具](../src/mcp/contact-answer-tools.ts)及[数据契约](../src/contracts/contact-graph.ts)为准。上传页面入口以已验证的功能分支实现为准，当前 main 的注册代码尚未包含该入口。

### 3.1 联系人搜索图谱 App

`search_contacts` 关联自包含的只读 MCP App，原输入、JSON 输出、筛选及排序不变。支持的宿主展开后先显示当前页命中节点，再自动读取各命中主体的全部一跳职业关系及后续分页，逐步显示直接关联节点、方向和关系类型；按真实 ID 去重，不递归展开补充节点。点击查看档案与来源，不清空图谱。提供进度、停止/继续、失败页重试、搜索翻页以及平移/缩放。

实线只表示已记录的正式关系，不代表人工审核或当前在职。只有原查询 `include_unverified:true` 才加载虚线；待核实来源仅为命中主体自身 claim，未覆盖其他主体指向它的入向 claim。画布和详情只展示任职、教育、项目、机构关联及职业相关证据，不展示家庭关系和联系方式。UI隐藏字段不等于服务端数据脱敏，已鉴权宿主仍可获得原工具完整响应。无 App 支持时继续文字/表格输出；无独立网页查询、写入或 LLM 分析功能。关联多时加载更久，未完成或失败必须明确标记。

## 4. 信息获取与证据

正式评估以已确认主体档案为起点，并行收集企查查和豆包搜索材料。企查查只接入 `qcc-company`、`qcc-risk`、`qcc-ipr`、`qcc-operation` 四类企业主体服务；优先采集融资和招聘，再采集招投标、企业简介、风险、专利、可用的股东/软件著作权/资质及年报信息。豆包搜索走 HTTP API，覆盖官网产品技术、研发工程、质量认证、PLM/QMS/PDM、CAD/CAE 招聘、招投标采购和扩产融资。动态查询使用最近一年的搜索范围。

公开网页中的企业简称、品牌或集团名称需要结合已确认主体的别名、官网域名、地址等线索判断归属。证据标记为法定主体、集团、子公司、品牌或未知，并记录匹配程度；不能把其他实体的信息直接算入目标主体。上游文本交由方舟提炼行业标签、事实、融资概况、冲突和证据引用；引用必须指向实际采集的材料。网页内容仅是待分析数据。

方舟按输入字节预算将去重材料拆批处理，成功批次合并，失败或未处理材料计入审计缺口。材料不会因首批装不下就默默消失；仍可能受批次、调用预算或上游失败限制。行业由方舟给出带证据的自由文本标签，仅用于展示，不参与产品机会等级、推荐产品或置信度。

`discover_contacts` 使用豆包搜索和方舟查找公开披露的企业负责人、研发/技术、数字化/IT、采购和质量负责人。只有姓名、职位、公司与来源页面能相互核对的候选才返回；无明确职位的专利发明人或招投标联系人不返回。该工具不返回邮箱、电话，也不保证仅凭网页就已确认法人主体。

可选 Zoho 来源按连接只读搜索 CRM `Accounts`，名称包含匹配或多候选时要求用户确认 `connection_id/account_id`，重新核验所选记录后读取关联 `Contacts` 全部分页。仅展示客户与联系人姓名、职位、各自 CRM 记录负责人及来源；不请求电话、邮箱或 Owner 对象中的联系方式。`source=all` 保留网页与 CRM 两组结果，单源失败不抹去另一源，跨来源或跨连接同名人员不自动合并。`complete=false`、`partial`、`failed` 或 `needs_confirmation` 明确表示未获得全量。CRM 记录不等于已核实法定主体或当前任职；不写入网页快照、SQLite、图谱或 Zoho。所有 MCP 用户共享服务端已授权连接及其 CRM 可见范围。

内部 CRM 首次授权采用所在区域 API Console 的 Self Client 短期授权码，再通过 POST 请求体换取 Refresh Token。最小 scopes 为 `ZohoCRM.modules.accounts.READ`、`ZohoCRM.modules.contacts.READ`、`ZohoSearch.securesearch.READ`、`ZohoCRM.settings.fields.READ`、`ZohoCRM.settings.modules.READ`、`ZohoCRM.settings.related_lists.READ`；不申请 users/org、settings.ALL 或写权限。服务端环境变量配置连接，SDK 在内存中按需刷新 Token；撤销后须重新授权。SDK 补丁由 postinstall 应用并在启用 Zoho 前校验，元数据使用可清理的临时 resourcePath；补丁不符或临时目录不可写时 Zoho 降级而网页继续。外部客户接入应改用 Server-based OAuth；真实 CRM 和宿主全量响应验收仍待专用测试授权。

共享联系人库与公开搜索分开：本地文件由 Python/Docling 读取正文与来源定位，LLM 归纳人物、机构、经历和关系，Node 校验结构与引文，提交后由 Rust 图谱进程持久化。实体包括 `Person`、`Organization`、`Project`；字段和关系遵循[联系人数据契约](superpowers/specs/contact-data-contract.md)。模型判断与文件来源可定位均不等于人工核实。共享库对所有有效 Token 可见和可维护，导入任务预览只对提交者可见，写操作记录操作者。

### 4.1 联系人数据模型

| 对象 | 保存内容与边界 |
| --- | --- |
| 人物 `Person` | 姓名、曾用名、描述、职位、技能、电话、邮箱、地址、网页、语言、知识领域、职业、证书、奖项等；可保存文件明确提供的性别、出生日期、国籍、出生地、居住地和工作地，不推断缺失的个人属性。姓名可缺省。 |
| 人物扩展 | 籍贯 `nativePlace`、爱好 `hobbies`、带可选时间的婚姻状态 `maritalStatus`、按平台与账号保存的即时通讯 `instantMessaging`。扩展字段明确与 Schema.org 标准属性区分。籍贯不等于出生地，婚姻状态不自动生成配偶关系。 |
| 组织 `Organization` | 公司、学校等机构统一为组织，保存名称、别名、法定名称、标识符、描述及可获得的联系方式。仅出现机构名不足以认定任职或就读。 |
| 项目 `Project` | 保存项目名称／描述；人物通过 `memberOf` 关联参与项目，项目通过 `clientOrganization` 关联服务的客户组织。客户不自动成为人物雇主；项目客户查询须核对两跳关系。 |
| 字段与关系证据 | 保存来源类型（文件、网页或手工）、相应值、采集时间，以及文件名、摘要哈希、短引文、页码等可用定位信息；冲突与历史证据保留，不因新值覆盖而假装原记录不存在。 |

电话、邮箱等支持多个值；`contactPoint` 可按联络用途分组，微信等保存平台、账号和可选标签。姓名变化可保留为 `alternateName`；相同姓名、本人手机、邮箱或账号只提供可能同人的建议，不自动合并。人工确认后可合并人物或在原 ID 补录姓名。

关系包括人物到组织的 `worksFor`、`alumniOf`、`affiliation`、`memberOf`，人物到项目的 `memberOf`，项目到客户组织的 `clientOrganization`，以及人物间的 `colleague`、`spouse`、`parent`／`children`。每段任职独立保存职位与起止日期；缺少结束日期不等于现任。现任判断须有 `employment_status=current` 及完整的 `status_as_of` 日期。`alumniOf` 表示就读／校友联系，不单独证明毕业或学位。

### 4.2 提取、弱线索与人工核对

字段归属遵循“实体保存自身信息，关系保存特定经历”：Person 保存个人身份、联系方式和技能；爱好、婚姻情况、籍贯及即时通讯账号位于 Person.extensions。Organization 仅保存学校／公司的自身信息，不保存某人的专业、学历、任职或就读时间。alumniOf.properties 可保存 major、educationLevel、startDate、endDate，均可省略；educationLevel 仅表示披露的教育层次，不证明毕业或取得学位。同校不同教育详情分开保存；旧空属性关系仍可读取。worksFor 和项目 memberOf 沿用现有角色／时间字段，项目描述与个人参与角色不得混淆。

上下文明确的错置教育／任职字段在抽取映射中纠正容器，再进行原有引文及值校验。失败字段进入 Person 上指向相应学校／雇主的关系待核实项，不污染机构。无法定位经历的 `$experience` 仅是审核线索，不能直接确认为 Person 属性；须核对主体、目标及原文后明确保存正确关系，再处理原线索。技能为空或可选经历字段无效不阻断有有效主体证据的联系人创建；主体歧义等原阻断规则不变。不自动迁移历史错误记录。

Docling 负责读出 PDF／图片中的文字及块定位；LLM 负责跨块理解主体、任职、教育、项目、客户和技能，避免依赖特定排版模板。正文分批仍受字节、批次、调用预算约束；适配器校验值类型、端点和引文所属原块，不把语义判断等同于正则命中。实现同类能力时尽可能参考 Docling Graph，但保留项目自己的数据契约与写入流程。

可靠且来源可定位的字段与关系可形成文件来源的正式图谱事实；其余可保存的线索带原因进入 `unverified_claims`，不因一个字段不可靠而丢弃整个档案。非法形状、过大内容或容量限制仍可能导致截断／未保存，须返回警告。报告处理范围与未处理块，不把未读取部分说成已保存。

默认检索与 `ask_contacts` 只使用正式事实。查待核实线索须以非空关键词 `query`、`mode=keyword`、`include_unverified=true` 显式查询，结果区分 `confirmed` 与 `unverified`；此模式不支持语义／混合检索。`confirmed` 表示正式图谱命中，不保证经过人工审核。客户查询返回 `matched_project_id`；待核实项目路径可能涉及人物与项目上的多个 `claim_ids`，须分别核对。`organization_id` 仍只按任职／就读过滤。

用户在聊天中用 `get_contact` 分页读取线索与证据，再用 `review_contact_claim` 确认、更正或拒绝；错误正式字段可用 `save_contact` 配合当前版本及修正证据维护。没有专门的完整档案编辑网页；上传页只负责选择文件、预览和确认。`ask_contacts` 不以待核实线索作事实，也不直接承担项目客户两跳问答。

### 4.3 简历／名片导入与提交

一份简历或名片只创建一个实质主体 `Person`。证明人、推荐人或紧急联系人不作为主体建档。无真实姓名和手机号的简历，只要有可定位的技能等实质字段，或明确归属于该主体的任职／就读证据，可保存匿名人物；不填“未知姓名”等占位姓名。匿名档案可按公司、学校、技能或客户线索查找，确认身份后在原 `entity_id` 补录。孤立机构名不能构成空白人物档案。

名片中唯一人物的姓名、公司与职位归属清楚时，无需另有“任职于”字样，即可形成文件来源的正式 `worksFor`，保存职位与名片引文；不推断任职日期，`employment_status` 保持 `unknown`，不等同于外部核验或确认当前在职。多人物、多公司、缺职位或版面归属不明时，只保留待核实组织线索。合成测试标识不作为任职证据，也不否定测试名片声明的关系；合成数据仍不是真实人物事实。简历中有来源的任职日期校验不变。

文字导入接受非空、最多 20,000 个 UTF-16 代码单元的原文，复用现有容量、限频、并发、超时、任务状态与确认流程；不增加网页入口或独立队列。用户文字会发送给配置的抽取模型。输入原文和 SHA-256 保存在导入任务中，正式字段／关系保存 `source_type=text`、`text_sha256` 与可定位的短引文，不伪造文件名或页码。用户提供的文字不等于外部核实，未知任职日期和当前状态不推断。预览不返回完整原文，普通日志不记录原文、模型响应或凭证。同一用户、文字及 `operation_id` 可回放；同一操作换内容则拒绝。

聊天／CLI 自动提交建立唯一主体，以及有证据的组织和与主体项目建议相连的项目；明确的任职、就读、项目参与和客户关系写为文件来源正式边，其余有效建议保留待核实状态。多个仍可提交且主体无法判定的人物、或没有可提交主体时，拒绝自动提交且不部分写入。需合并、修改或跳过时使用手工选择；同一文件仍不能创建两个人物。文件重复与身份匹配只提示，不自动跨文件合并。

上传页面必须展示完整预览、候选、字段、短证据、关系建议、待核实项、重复建议及处理范围。只有服务端明确允许确认时启用按钮；主体不明确、预览缺失／未完整、原件存在未处理块、匹配失败或截断、可能重复等会阻止直接确认。提交前服务端再次校验权限、同一预览版本和确认规则；版本冲突重新加载完整预览，由用户再次核对并点击。聊天工具不能自动绕过页面阻断；用户另行明确要求人工处理时先读原任务完整预览。

`ready_for_review` 仅表示预览可读，上传成功或 OCR 成功均不表示已入库。完成提交后回读档案及关系，并分别报告已保存事实、待核实线索、未处理范围与警告。同一操作原样重试是幂等回放，不重新提取，也没有自动断点续跑；重新导入可能产生重复提示。

`ask_company` 只接受当前缓存中已确认、名称和信用代码一致的主体。指定 `assessment_id` 时，报告还须已完成且属于同一主体；否则返回 `failed`。它优先复用 30 天内、与问题相关且非动态的报告精简证据快照；旧报告没有快照、问题要求近期动态或快照不相关时，才定向补查。补查最多调用 1 次企查查、2 次豆包搜索和 1 次方舟，不启动完整七产品评估。复合问题按主题安排搜索并兼顾不同主题的证据；模型输入有容量上限，未纳入材料的数量会在回答中说明。新补查材料和追问答案不另行保存，原报告及机会等级不改变。

追问的正文区分“资料直接支持”“可能的解释，但未获证实”“仍需核实”；复合问题缺少某一主题的可支持结论时列出“尚未回答”，状态为 `insufficient`，已核实的部分仍保留。引用只指向实际纳入的证据；网页给直达 URL，企查查无直达链接则明示。仅凭招聘资料不能断言软件采购计划，资料不全时不能把“未查到”写成“企业不存在”。单一来源失败可用剩余证据回答并标注限制；无足够证据为 `insufficient`，主体校验、方舟调用或同步时限失败为 `failed`。

## 5. 产品机会判断

固定评估七项：PTC Windchill、Feigenbaum QMS、PTC Creo、Dassault Systèmes CATIA、Dassault Systèmes Abaqus、CST Studio Suite、Dassault Systèmes SolidWorks。每项输出机会等级 `高/中/低/待核实`、证据置信度 `高/中/低`、理由、阻碍和缺口。没有分数或星级。

方舟负责从文本提炼可引用事实；最终机会等级由确定性规则计算。产品或工程方法的直接证据是起点，研发、质量、制造复杂度和已使用软件提供支撑，近期招聘、采购、扩产或融资提供时机。明确预算冻结、暂停采购、替代系统等是阻碍。缺少公开决策权信息本身不扣分；招聘中点名软件不等于已部署或准备采购。

当前等级规则的关键边界：

- 最近 90 天内，归属确认、直接点名目标产品且仍表达采购计划的正式采购/招标公告，可由单条证据判为“高”；已中标、成交、结束、取消或暂停的公告不走该路径。关键主体或来源冲突仍优先判“待核实”。
- 普通“高”需要已确认的具体产品/工程场景、匹配复杂度、最近 365 天的时机，以及没有已知明确阻碍；不要求第二个发布方或正向预算证明。
- “中”需要已确认场景及可靠的复杂度或软件生态支撑，但高机会条件未齐备；其余依证据强弱、归属和阻碍落入“低”或“待核实”。
- 最近 365 天且归属确认的融资可作为企业活跃或扩张时机，不能单独证明任何产品预算、采购意向或产品场景。行业标签不设准入门槛。
- 置信度描述产品证据的支持程度：符合正式采购条件或有多个独立发布方时可为“高”；一个可靠发布方为“中”；弱证据、未确认归属或无相应支持为“低”。它不改变机会等级。

综合机会取最高的有效产品等级；同级先看已确认的直接证据数量，再看阻碍数量，最后按固定产品顺序决定推荐项。只有弱证据或主体归属不明时，综合机会为“待核实”、推荐产品为 `null`。综合机会当前只是七产品机会的聚合，不是账户优先级、购买阶段或成交概率。

## 6. 报告要求

完成报告必须保留：客户摘要、七产品机会矩阵、可用的产品切入依据、关键证据、销售建议、风险、分层缺口和来源状态。即使没有推荐产品，也展示七产品矩阵；没有内容的“产品切入依据”章节不显示。

客户摘要含法定主体、行业标签、规模线索、最近融资、最佳切入产品、综合机会和核心理由。关键证据展示事实、被提及主体及归属、匹配依据、来源、时间和支持的结论。只把真实 HTTP(S) 直接 URL 渲染为链接；企查查未给直接链接时明确写“来源链接不可用”，不猜测链接。最近融资可用简要文本表达，不要求日期、轮次或金额完整。

销售建议包括推荐产品、目标岗位、基于已核实事实的首轮访谈问题和下一步行动。上游失败、方舟未提炼、来源链接缺失等系统或审计问题留在缺口，不交给销售“访谈确认”。动态信号在报告完成 7 天后读取时标记为 `stale` 并提示复核；报告本身可在 30 天内继续缓存复用。

报告不得根据高管年龄推断决策风格，不用员工数乘行业人效估算真实营收，不把融资解释为项目预算，也不编造采购意向。

## 7. 状态、缓存与失败

基础画像和已完成报告默认各缓存 30 天，分别由 `PROFILE_CACHE_TTL_DAYS` 和 `ASSESSMENT_CACHE_TTL_DAYS` 配置。同一信用代码只允许一个 `processing` 评估任务。新完成报告的精简证据快照可在采集后 30 天内按需复用；旧报告无快照时不会从 Markdown 反推证据。公开网页 `discover_contacts` 按规范化的查询词与地域缓存 30 天，简称和全称不会自动合并；每次实际刷新都追加快照，历史联系人只表示旧快照曾见到的任职证据，不代表已离职。共享联系人库是另一个持久化数据库，不受此 30 天缓存期限影响；旧快照可同步为待核实线索，不能凭同名跨来源自动认定为一人或恢复已归档档案。

企查查或豆包搜索部分失败时，以仍可用的证据生成报告并标记 `partial/failed`。两者都没有可用材料时，只要方舟仍完成一次有效整理，报告可完成并将产品标为“待核实”；所有方舟批次均失败时任务为 `failed`。单个上游请求最多再试一次；确定性不可重试错误直接失败并标注。联系人查询在刷新失败而存在旧快照时返回旧结果与警告，否则返回工具错误。

任务记录、画像、报告及公开联系人快照保存在原单实例 SQLite。共享联系人库启用时使用独立 SQLite 文件，由 Rust 图谱进程管理；Node 负责 MCP、上传、模型抽取和任务协调。进程重启时，遗留 `processing` 的评估及联系人导入任务转为 `failed`；评估队列按 FIFO 执行，联系人文档抽取默认同时处理一项。原缓存到期只影响复用资格，不删除旧记录；已经提交的图谱事实不会因重启回滚。

文件导入默认最多保留 10 个待处理文件，每文件 20 MB、PDF 50 页、图片 2500 万像素；上传临时空间最多 1 GiB。提取每个完整模型请求默认上限 32000 UTF-8 字节，最多 8 批／16 次模型调用；超出或失败时明确标记处理缺口。模型和端点通过服务配置选择，不在产品中承诺固定模型名；联系人提取请求当前显式启用 `thinking`，该设置不代表提取准确率保证。

## 8. 安全、部署与已知边界

服务端使用每用户独立 Bearer Token，保存哈希、用户标识、启用状态和创建时间；管理员通过 CLI 创建、列出元数据和禁用 Token。任一有效 Token 知道报告 UUID 后可读取该报告，企业评估没有跨用户报告隔离或配额。联系人导入仍校验任务归属；上传尝试和新导入分别按认证用户每 60 秒最多 5 次，同用户多个 Token/页面会话共用额度。已创建任务的幂等重试不计数，限流不删除已上传原件；HTTP 返回 429/等待秒数，MCP 返回明确工具错误。计数仅单实例内存保存，重启清零。`/mcp` 校验 Host、配置允许的 HTTPS Origin 和 Token；无 Origin 的非浏览器客户端仍须带 Token。健康检查为 `/healthz`。

部署为单副本 Node.js 24/TypeScript 服务，SQLite 文件放在持久化挂载目录，一个数据库文件由一个服务实例拥有。`CONTACT_GRAPH_ENABLED` 默认为 `false`，须配置独立的 `CONTACT_GRAPH_SQLITE_PATH` 与 `CONTACT_GRAPH_BIN`。语义／混合检索另需独立的 `ARK_EMBEDDING_API_URL`、`ARK_EMBEDDING_MODEL`、`ARK_EMBEDDING_CREDENTIAL`；不配置时关键词检索仍可用。生产凭据和上游地址通过环境变量注入，公网 HTTPS 由前置代理终止。报告仅持久化 Markdown、必要元数据、精简审计结果及可空的精简证据快照，不保存完整上游原始正文；`ask_company` 的补查和答案不持久化。

上传部署将服务与 Docling broker 分为同版本的两个容器，服务通过 `CONTACT_WORKER_SOCKET` 请求解析。只维护普通容器运行方式，不依赖 Landlock、libseccomp 或应用安装的 seccomp。Worker 保持非 root、只读根、移除全部 capability、no-new-privileges、默认容器 seccomp 和资源限额，不接收上游密钥、不挂载数据库；Sealos 关闭 service-account Token 自动挂载。安全边界为容器，不承诺逐文件内容隔离或同 Pod 禁网；Compose 保留无网络配置。初始额度 4 GiB/2 CPU，Compose 64 PID，Sealos PID 上限由节点管理，均非已验证最低要求。解析器不再设置 AS/NPROC，保留 CPU 120 秒、128 FD、单文件 256 MiB、禁 core dump、环境白名单、离线模型和线程控制。预检/解析墙钟限制 30/120 秒，结束、错误、超时或取消后清理普通后代进程组，不承诺阻止恶意另建 session。Sealos 上传与解析 `/tmp` 各为 1 GiB 磁盘 emptyDir，socket 为 1 MiB 内存卷。构建与生产容器验证仅在远程 CI 执行，本项目禁止本地构建。

上传页面使用单文件、最多一个导入任务的受限会话，固定有效期 2 小时；外部链接仅含有效期 60 秒、一次兑换的交接码。页面不接收长期 Token；App 凭据只在内存中，外部页使用受限 HttpOnly Cookie。App 刷新／关闭后旧内存会话不可恢复；外部页刷新可尝试 Cookie 恢复，过期、服务重启或退出后重开。真实 `import_id` 可用于有权用户在聊天查进度，本身不提供授权。来源 Token 被禁用时会话失效。

确认成功后撤销会话的新操作权限；若响应丢失，仅以原凭据、同一预览版本重试固定成功回执，受原会话期限、Token 禁用、退出、进程重启与回执容量淘汰限制。不能因回执重试失败就断定没有入库，应查询原任务。退出页面不回滚已写入资料，也不自动取消后台任务；取消须对原导入任务明确执行。

选文件前告知原件临时保存、提取文字发送给配置的模型、提交后写入团队共享库。临时原件置于 `/data` 和数据库备份范围之外，完成、失败、取消或到期时清理；清理失败如实报告。图谱只保留必要字段、短证据与可用定位，不持久化完整原件或 OCR 正文。网页和文件内容均作为不可信数据处理，预览按纯文本渲染。个人联系方式不得自动写入 `discover_contacts` 的公开搜索响应。

当前未提供完整联系人管理后台、飞书／Zoho 写回、批量评估、账户级 ABM 优先级、自动任务恢复、历史图谱数据自动删除或生产完成时限 SLA。真实报告和文件提取仍依赖上游可用性、可核实主体、文件质量与公开资料覆盖度。上传页不提供简历排版编辑、通用文档管理或自动联系人合并。

## 9. 当前验收口径

- 用户可从基础画像确认主体，按需查询联系人，再提交正式评估并凭 UUID 读取结果。
- 联系人库启用后，可导入 PDF/JPG/JPEG/PNG；每文件只有一个人物主体，可保存有实质证据的匿名档案，记录多段任职、学校、技能及项目客户。聊天／CLI 可按授权自动提交，页面必须完整预览后点击确认；同名或号码相同不自动合并，公开 `discover_contacts` 仍不返回电话或邮箱。
- 可靠字段与关系入正式图谱，可保存的弱线索标记为待核实；可按学校、公司和项目客户关键词显式包含弱线索检索。确认、拒绝、编辑、归档及恢复均有版本和操作记录，默认问答不使用待核实线索。
- 综合查询可完成共享库检索、公开公司岗位搜索、档案证据核对，也可只执行用户指定环节；姓名相似与公开网页匹配不能自动证明同一人或现任关系。
- 已确认主体可不提交正式评估而同步追问；能引用旧报告证据，也能按问题定向补查。部分问题无证据时保留已核实内容并标明“尚未回答”，不把招聘或融资推断为软件采购意向。
- 完成报告始终保留七产品矩阵，证据和缺口可追溯；无直接链接时明示不可用。
- 机会等级由规则决定，行业仅展示；融资不构成项目预算；关键冲突不被普通正向信号覆盖。
- 失败来源、未处理材料、模型批次失败与动态信息过时均明确展示；任务不会永久保持旧的 `processing` 状态跨重启。
- 缓存、强制刷新和同主体进行中任务复用遵循上文行为；历史报告和联系人快照仍可在 SQLite 中保留。

### 9.1 已有验证证据

## 企业与联系人资料复用增量（2026-10-12）

企业画像、组织搜索摘要、组织详情与历史报告、人物任职公司背景问答、企业联系人与客户项目问答、报告后续变化目录共用已有 SQLite 仓储和原生图谱。首版不建设独立统一主体库、全局证据库或聚合缓存，不自动合并组织，不改写历史报告。浏览资料不触发外部调查或正式评估；问答中库外或动态问题保留已有定向补查流程。

三个读取工具以 `include_company_context:true` 请求附加信息；报告通过 `include_related_updates:true` 请求变化目录。启用企业关联服务后只新增一个模型可见工具 `link_company`，实际总数由图谱、上传及其他可选服务决定。人工确认和解除需组织版本、关联版本、稳定操作 ID、审核说明及认证 actor；自动关联只读，解除保留抑制标记。唯一同名、无有效代码或无身份依据的候选不视为 confirmed；身份变化和代码矛盾产生冲突。一个组织同一时刻最多关联一家企业，多个组织可指向同一企业。

只有 confirmed 关联可用于统计、展示与事实回答。企业概览按人物与项目 ID 去重，不包含家庭关系或直接联系方式。学校关系不能作为就业，unknown 不能表述为现任。未知或不完整统计返回完整性信息而非虚构零值。历史报告目录独立使用 report_offset/report_limit（默认 10，上限 50），原文读取不扩展报告权限；图谱 App 限制当前节点目录，企业问答校验显式报告主体。

旧画像可以展示并标记 stale，企业问答仍要求新鲜主体画像。问答跨库材料最多 20 条、相关图谱档案最多 12 个，最多读取最新一个已完成报告快照；context_citations 只记录实际纳入且引用的材料。同一文件重复导入不形成多个独立来源。related_updates 首版最多 20 条，按入库记录时间倒序，明确 since、scope、truncated 及不可用来源，不能解释为现实事件时间线。

此增量的最终 tested SHA、Chromium 与真实宿主状态见[验收记录](validation/2026-10-12-company-contact-data-reuse.md)。最终 gate 和真实 Codex／ChatGPT 验收尚未完成，不能标为整体验收通过。
