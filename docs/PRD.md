# 目标客户体检与联系人管理 MCP 产品需求文档

状态：当前 `main` 分支的已实现功能基线（截至 2026-09-26）。共享联系人库代码已实现但默认关闭；本文件不表示它已在现有线上环境启用或包含在此前发布的镜像中。设计与实施依据见 [联系人管理升级计划](superpowers/plans/2026-09-25-contact-management-upgrade.md)，操作说明见 [快速入门](QUICKSTART.md)及[联系人管理 skill](../skills/salestools-contact-management/SKILL.md)。

## 1. 产品目标与用户

面向使用 Codex 的 B2B 销售人员：先用企业名称了解基本情况；确认法定主体后，可追问具体问题，也可按需生成有来源依据的中文销售评估报告。找人时可以搜索公开网页的关键岗位人员；启用共享联系人库后，还可导入和维护经人工确认的人物、组织、任职与关系。产品帮助销售选择值得访谈的方向，不预测成交概率，也不把招聘或融资直接视作采购意向。

当前交付形态是部署于中国大陆云的远程 MCP 服务，客户端通过 HTTPS `/mcp` 访问。没有网页界面、飞书或 Zoho CRM 集成。

## 2. 用户流程

1. 用户说“了解这家公司”或意图不明确时，调用 `get_company_profile`。返回候选法定主体及可获得的基础画像；多候选时由用户确认，不自动选择。
2. 需要公开岗位线索时调用 `get_contacts`；需要已确认的团队共享档案时，若联系人库已启用则调用 `search_contacts`、`get_contact` 或 `ask_contacts`。这两套数据不能混为一谈。
3. 导入本地简历或名片时，先通过鉴权的 `/contact-files` 上传 PDF/JPG/PNG，或使用 `contacts:upload` CLI；单文件最多 20 MB，PDF 最多 50 页。再提交 `file_id` 启动抽取。查看候选、引文和重复建议，人工校正并确认创建、合并或跳过后，才写入正式档案。
4. 用户已确认法定名称与 18 位统一社会信用代码，并想了解特定问题时，调用 `ask_company`；无需先生成正式报告。它同步返回带引用的回答或明确的证据不足、失败状态，不改写已有报告。
5. 用户明确要求正式评估后，调用 `submit_assessment`。评估执行时需要能读取到匹配且未过期的主体画像；如果没有，任务会失败并提示主体信息不可用。任务异步处理；重复主体优先复用进行中任务或 30 天内已完成报告。
6. 使用 `assessment_id` 调用 `get_assessment_status`，状态为 `processing`、`completed` 或 `failed`。完成后调用 `get_assessment_report` 阅读 Markdown 报告；处理中或失败时返回状态消息。

新任务返回 `estimated_minutes: "5-40"`，只是经验区间，不含排队时间，也不是完成时限承诺。`force_refresh=true` 跳过已完成报告缓存，但仍复用同一主体的进行中任务。

## 3. MCP 工具

| 工具 | 关键输入 | 当前输出与边界 |
| --- | --- | --- |
| `get_company_profile` | `query`，可选 `region_hint` | `candidates`、`basic_profile`、`source_status`、`cache_hit`；只用企查查，唯一且名称匹配的主体才补充基础画像；上游不可用时明确失败。 |
| `get_contacts` | `query`，可选 `region_hint` | 最多 3 家企业、每家最多 10 名当前联系人及最多 10 条历史任职证据；返回来源 URL、发布时间、采集时间及警告。 |
| `submit_assessment` | `legal_name`、`credit_code`，可选 `force_refresh` | 新建或复用任务，返回 `assessment_id`、`status`、`cache_hit`；新任务附预计时间，缓存命中附 `cached_at`。 |
| `get_assessment_status` | `assessment_id` | 返回三态及简短进度或失败消息。 |
| `get_assessment_report` | `assessment_id` | 完成时返回 Markdown、综合机会、推荐产品、采集时间、动态信号新鲜度与来源状态；其他状态只返回状态消息。 |
| `ask_company` | `legal_name`、`credit_code`、`question`，可选 `assessment_id` | 对已确认主体同步追问；返回 `answered/insufficient/failed`、Markdown、是否补查、采集时间与实际引用来源；不修改七产品评估。 |

上述六个基础工具保持可用。启用 `CONTACT_GRAPH_ENABLED=true` 并配置独立图谱数据库和 Rust 可执行文件后，服务注册以下共享联系人库工具：

| 工具 | 当前行为与边界 |
| --- | --- |
| `import_contacts`、`get_contact_import`、`commit_contact_import`、`cancel_contact_import` | 依据已上传的 `file_id` 异步抽取、分页预览、人工确认提交或取消；抽取不等于入库。导入状态为 `queued/processing/ready_for_review/committed/failed/cancelled`。 |
| `search_contacts`、`get_contact` | 在共享库按姓名、组织、职位、技能或关键词检索，分页读取档案、证据、冲突及关系；语义/混合检索需要嵌入端点，可用性不足时退回关键词并给出警告。 |
| `save_contact`、`merge_contacts`、`delete_contact` | 创建、版本化编辑、明确恢复或归档人物/组织；人工合并仅限人物。删除为归档，不是清除历史证据。 |
| `save_contact_relation`、`delete_contact_relation` | 保存或归档有依据的任职、组织及人物关系；每段任职可独立保留职位和时间。 |
| `ask_contacts` | 依据库内实体、关系及短证据回答人物关系和任职问题；返回 `answered/clarify/insufficient/failed`，同名或证据不足时不猜测。 |
| `retry_contact_index` | 仅在嵌入服务已配置时，重试失败的联系人向量索引。 |

写入操作使用稳定 `operation_id` 安全重试，修改和合并需当前版本；合并目标、字段取舍及导入候选选择由用户确认。工具的准确参数和结果以 [联系人 MCP 注册](../src/mcp/contact-tools.ts)、[导入工具](../src/mcp/contact-import-tools.ts)、[检索工具](../src/mcp/contact-search-tools.ts)、[问答工具](../src/mcp/contact-answer-tools.ts)及[数据契约](../src/contracts/contact-graph.ts)为准。

## 4. 信息获取与证据

正式评估以已确认主体档案为起点，并行收集企查查和豆包搜索材料。企查查只接入 `qcc-company`、`qcc-risk`、`qcc-ipr`、`qcc-operation` 四类企业主体服务；优先采集融资和招聘，再采集招投标、企业简介、风险、专利、可用的股东/软件著作权/资质及年报信息。豆包搜索走 HTTP API，覆盖官网产品技术、研发工程、质量认证、PLM/QMS/PDM、CAD/CAE 招聘、招投标采购和扩产融资。动态查询使用最近一年的搜索范围。

公开网页中的企业简称、品牌或集团名称需要结合已确认主体的别名、官网域名、地址等线索判断归属。证据标记为法定主体、集团、子公司、品牌或未知，并记录匹配程度；不能把其他实体的信息直接算入目标主体。上游文本交由方舟提炼行业标签、事实、融资概况、冲突和证据引用；引用必须指向实际采集的材料。网页内容仅是待分析数据。

方舟按输入字节预算将去重材料拆批处理，成功批次合并，失败或未处理材料计入审计缺口。材料不会因首批装不下就默默消失；仍可能受批次、调用预算或上游失败限制。行业由方舟给出带证据的自由文本标签，仅用于展示，不参与产品机会等级、推荐产品或置信度。

`get_contacts` 使用豆包搜索和方舟查找公开披露的企业负责人、研发/技术、数字化/IT、采购和质量负责人。只有姓名、职位、公司与来源页面能相互核对的候选才返回；无明确职位的专利发明人或招投标联系人不返回。该工具不返回邮箱、电话，也不保证仅凭网页就已确认法人主体。

共享联系人库与公开搜索分开：本地文件由 Python/Docling 解析，Node/方舟抽取候选与短引文，用户审核后由 Rust 图谱进程持久化。正式业务实体为 `Person` 和 `Organization`，人物属性、项目扩展、关系方向和字段级证据遵循[联系人数据契约](superpowers/specs/contact-data-contract.md)。同名不足以自动认定身份；本人号码、邮箱或账号的重合只提供匹配建议，不自动合并。组织名称或名片抬头也不自动证明当前任职。`worksFor` 可存多段经历，缺少结束日期不等于仍在职。原文件及完整 OCR 正文不长期保存，正式档案保留必要短引文和可核实页码。共享库对所有有效 Token 可见和可维护，导入任务预览只对提交者可见，写操作记录操作者。

`ask_company` 只接受当前缓存中已确认、名称和信用代码一致的主体。指定 `assessment_id` 时，报告还须已完成且属于同一主体；否则返回 `failed`。它优先复用 30 天内、与问题相关且非动态的报告精简证据快照；旧报告没有快照、问题要求近期动态或快照不相关时，才定向补查。补查最多调用 1 次企查查、2 次豆包搜索和 1 次方舟，不启动完整七产品评估。复合问题按主题安排搜索并兼顾不同主题的证据；模型输入有容量上限，未纳入材料的数量会在回答中说明。新补查材料和追问答案不另行保存，原报告及机会等级不改变。

追问的正文区分“资料直接支持”“可能的解释，但未获证实”“仍需核实”；复合问题缺少某一主题的可支持结论时列出“尚未回答”，状态为 `insufficient`，已核实的部分仍保留。引用只指向实际纳入的证据；网页给直达 URL，企查查无直达链接则明示。仅凭招聘资料不能断言软件采购计划，资料不全时不能把“未查到”写成“企业不存在”。单一来源失败可用剩余证据回答并标注限制；无足够证据为 `insufficient`，主体校验、方舟调用或同步时限失败为 `failed`。

## 5. 产品机会判断

固定评估七项：PTC Windchill、Feigenbaum QMS、PTC Creo、Dassault Systèmes CATIA、Dassault Systèmes Abaqus、CST Studio Suite、Dassault Systèmes SolidWorks。每项输出机会等级 `高/中/低/待核实`、证据置信度 `高/中/低`、理由、阻碍和缺口。没有分数或星级。

方舟负责从文本提炼可引用事实；最终机会等级由确定性规则计算。产品或工程方法的直接证据是起点，研发、质量、制造复杂度和已使用软件提供支撑，近期招聘、采购、扩产或融资提供时机。明确预算冻结、暂停采购、替代系统等是阻碍。缺少公开决策权信息本身不扣分；招聘中点名软件不等于已部署或准备采购。

当前等级规则的关键边界：

- 最近 90 天内，归属确认、直接点名目标产品且仍表达采购计划的正式采购/招标公告，可由单条证据判为“高”；已中标、成交、结束、取消或暂停的公告不走该路径。关键主体或来源冲突仍优先判“待核实”。
- 普通“高”需要已确认的具体产品/工程场景、匹配复杂度、最近 365 天的时机，以及没有已知明确阻碍；不要求第二个发布方或正向预算证明。
- “中”需要已确认场景及可靠的复杂度或软件生态支撑，但高机会条件未齐备；其余依证据强弱、归属和阻碍落入“低”或“待核实”。
- 最近 365 天且归属确认的融资可作为企业活跃或扩张时机，不能单独证明任何产品预算、采购意向或产品场景。行业标签不设准入门槛。
- 置信度描述产品证据的支持程度：符合正式采购条件或有多个独立发布方时可为“高”；一个可靠发布方为“中”；弱证据、未确认归属或无相应支持为“低”。它不改变机会等级。

综合机会取最高的有效产品等级；同级先看已确认的直接证据数量，再看阻碍数量，最后按固定产品顺序决定推荐项。只有弱证据或主体归属不明时，综合机会为“待核实”、推荐产品为 `null`。综合机会当前只是七产品机会的聚合，不是账户优先级、购买阶段或成交概率。

## 6. 报告要求

完成报告必须保留：客户摘要、七产品机会矩阵、可用的产品切入依据、关键证据、销售建议、风险、分层缺口和来源状态。即使没有推荐产品，也展示七产品矩阵；没有内容的“产品切入依据”章节不显示。

客户摘要含法定主体、行业标签、规模线索、最近融资、最佳切入产品、综合机会和核心理由。关键证据展示事实、被提及主体及归属、匹配依据、来源、时间和支持的结论。只把真实 HTTP(S) 直接 URL 渲染为链接；企查查未给直接链接时明确写“来源链接不可用”，不猜测链接。最近融资可用简要文本表达，不要求日期、轮次或金额完整。

销售建议包括推荐产品、目标岗位、基于已核实事实的首轮访谈问题和下一步行动。上游失败、方舟未提炼、来源链接缺失等系统或审计问题留在缺口，不交给销售“访谈确认”。动态信号在报告完成 7 天后读取时标记为 `stale` 并提示复核；报告本身可在 30 天内继续缓存复用。

报告不得根据高管年龄推断决策风格，不用员工数乘行业人效估算真实营收，不把融资解释为项目预算，也不编造采购意向。

## 7. 状态、缓存与失败

基础画像和已完成报告默认各缓存 30 天，分别由 `PROFILE_CACHE_TTL_DAYS` 和 `ASSESSMENT_CACHE_TTL_DAYS` 配置。同一信用代码只允许一个 `processing` 评估任务。新完成报告的精简证据快照可在采集后 30 天内按需复用；旧报告无快照时不会从 Markdown 反推证据。公开网页 `get_contacts` 按规范化的查询词与地域缓存 30 天，简称和全称不会自动合并；每次实际刷新都追加快照，历史联系人只表示旧快照曾见到的任职证据，不代表已离职。共享联系人库是另一个持久化数据库，不受此 30 天缓存期限影响；旧快照可同步为待核实线索，不能凭同名跨来源自动认定为一人或恢复已归档档案。

企查查或豆包搜索部分失败时，以仍可用的证据生成报告并标记 `partial/failed`。两者都没有可用材料时，只要方舟仍完成一次有效整理，报告可完成并将产品标为“待核实”；所有方舟批次均失败时任务为 `failed`。单个上游请求最多再试一次；确定性不可重试错误直接失败并标注。联系人查询在刷新失败而存在旧快照时返回旧结果与警告，否则返回工具错误。

任务记录、画像、报告及公开联系人快照保存在原单实例 SQLite。共享联系人库启用时使用独立 SQLite 文件，由 Rust 图谱进程管理；Node 仍负责 MCP、上传、抽取和任务协调。进程重启时，遗留 `processing` 的评估及联系人导入任务转为 `failed`；评估队列按 FIFO 执行，联系人文档抽取默认同时处理一项。原缓存到期只影响复用资格，不删除旧记录。

## 8. 安全、部署与已知边界

服务端使用每用户独立 Bearer Token，保存哈希、用户标识、启用状态和创建时间；管理员通过 CLI 创建、列出元数据和禁用 Token。任一有效 Token 知道报告 UUID 后可读取该报告，当前没有跨用户报告隔离、配额或限流。`/mcp` 校验 Host、配置允许的 HTTPS Origin 和 Token；无 Origin 的非浏览器客户端仍须带 Token。健康检查为 `/healthz`。

部署为单副本 Node.js 24/TypeScript 服务，SQLite 文件放在持久化挂载目录。联系人库启用时，由 Node 管理本机 Python 文档解析进程及 Rust 图谱进程；`CONTACT_GRAPH_ENABLED` 默认为 `false`，还须配置独立的 `CONTACT_GRAPH_SQLITE_PATH` 与 `CONTACT_GRAPH_BIN`。语义/混合检索另需独立方舟嵌入端点；不配置时关键词检索仍可用。生产凭据和上游地址通过环境变量注入；公网 HTTPS 由前置代理终止。企查查、豆包搜索、方舟均有独立调用配置和总预算，普通日志记录任务与上游调用结果。报告仅持久化 Markdown、必要元数据、精简审计结果及可空的精简证据快照，不保存完整上游原始正文；`ask_company` 的补查和答案不持久化。

当前未提供网页 UI、飞书/Zoho 写回、批量评估、账户级 ABM 优先级、自动任务恢复、历史数据自动删除或生产完成时限 SLA。真实报告仍依赖上游可用性、可核实主体和公开资料覆盖度。

## 9. 当前验收口径

- 用户可从基础画像确认主体，按需查询联系人，再提交正式评估并凭 UUID 读取结果。
- 联系人库启用后，可上传本地 PDF/JPG/PNG，经抽取预览、明确选择和幂等提交形成共享档案；同名不自动合并，旧 `get_contacts` 仍不返回电话或邮箱。可检索、查看证据与任职、编辑/归档/恢复及引用库内证据问答。
- 已确认主体可不提交正式评估而同步追问；能引用旧报告证据，也能按问题定向补查。部分问题无证据时保留已核实内容并标明“尚未回答”，不把招聘或融资推断为软件采购意向。
- 完成报告始终保留七产品矩阵，证据和缺口可追溯；无直接链接时明示不可用。
- 机会等级由规则决定，行业仅展示；融资不构成项目预算；关键冲突不被普通正向信号覆盖。
- 失败来源、未处理材料、模型批次失败与动态信息过时均明确展示；任务不会永久保持旧的 `processing` 状态跨重启。
