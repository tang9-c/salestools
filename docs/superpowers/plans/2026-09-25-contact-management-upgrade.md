状态：工程审查完成，D1–D7 已确认并写回；已按用户要求补齐 Schema.org 首版数据契约，并确认 Docling 解析 + Node 抽取选型；补充内容尚未独立复审；尚未开始实现，运行与质量门槛须在实施时验证。

逐任务的代码、测试与交付顺序见 [联系人管理升级 Implementation Plan](2026-09-26-contact-management-implementation.md)；本文件作为产品与数据契约依据保留。

## 1. 目标与已确定范围

将现有“公开联系人搜索＋历史快照”升级为全员共享的 MCP 联系人库，支持文件导入、档案编辑、合并去重、关系管理、向量检索及带来源问答。

- 必须接入 `sqlite-knowledge-graph` Rust 库。
- 直接依赖 Docling 处理文档解析与 OCR；优先参考 Docling Graph 已有同类功能的源码与测试（包括模板、分块和来源追踪），由 Node 实现固定联系人抽取层并复用现有火山方舟客户端。不依赖或 fork Docling Graph；向量生成使用独立方舟嵌入端点。
- 本地文件通过鉴权上传接口及 CLI 提交，抽取结果经预览、校正和确认后入库。
- 首版支持中英文 PDF、JPG、PNG；每文件最多 20 MB，PDF 最多 50 页。
- 不长期保存原文件、页面图片或完整 OCR 正文；保留文件名、SHA-256、必要短引文和可核实的页码。
- 所有有效 Token 可查询和维护共享联系人，操作记录实际 `userId`。
- 不新增网页管理台；原网页搜索的岗位、电话和邮箱边界保持不变。

Schema.org 用于规范业务词汇；准确性由证据、校验和人工确认共同保证。

## 2. 架构与数据规则

### 运行架构

保留 Node.js／TypeScript 主服务，新增两个受其管理的进程：

| 组件 | 职责 |
|---|---|
| Node 主服务 | 鉴权、上传、MCP 工具、任务调度、分批调用方舟抽取、候选与引文校验、预览确认、模型问答和向量调用 |
| Python 文档进程 | 直接调用 Docling 解析与 OCR，输出带块 ID、页码和来源定位的文本块；不调用大模型、不创建联系人图谱 |
| Rust 图谱进程 | 调用指定库，独占联系人图谱数据库，执行事务、实体关系操作及向量查询 |

进程间使用固定业务命令的 JSON Lines 协议，带协议版本、请求 ID 和结构化错误，日志输出到 stderr。首版图数据库请求串行执行，文档抽取并发固定为 1；复用现有队列模式，不建设通用进程框架、消息总线或分布式任务系统。只开放明确业务操作，不提供任意 SQL、命令或客户端指定文件路径。请求 ID 用于匹配通信响应，不替代下述持久化操作 ID。

Rust 使用真实 `KnowledgeGraph` API；不采用目前部分函数仅返回说明信息的动态扩展接口。[源码依据](https://github.com/hiyenwong/sqlite-knowledge-graph/blob/main/src/extension.rs)

现有业务数据库继续保存鉴权、评估和公开搜索缓存；新联系人数据库保存正式档案、关系、证据、导入任务与审计。Python 不直接写数据库。

### 文档提取选型与职责边界（用户已确认）

选择“Docling 解析 + Node 固定联系人抽取层”。[Docling](https://github.com/docling-project/docling) 是运行时依赖；[Docling Graph](https://github.com/docling-project/docling-graph) 作为同类功能的优先源码与测试参考，不作为首版运行依赖、不复制整套管线、不生成中间 NetworkX 图。它提供结构化抽取、分块与来源追踪，直接依赖本来是可行选项；本项目已经自行管理稳定身份、人工合并和 Rust 图谱，采用薄抽取层以减少重复适配。此判断是架构选择，不是已测得的性能或质量优势。

```text
本地 PDF/JPG/PNG
  -> Python / Docling：解析、OCR、文本块及页码
  -> Node / 方舟：有限分批、固定契约抽取、字段与引文校验
  -> 待确认候选：用户修正、选择新建/合并/跳过
  -> Rust / SQLite 图谱：事务保存实体、关系、短证据
```

- Python 返回固定文本块契约：`block_id`（任务内唯一）、`text`、可选 `page`（从 1 开始）及 `source_ref`（Docling 项目引用）。引用与页码必须来自解析结果，无法定位时省略；不从模型生成页码。Pydantic 若用于解析输出校验，仅承担该契约，不维护另一份联系人抽取模型。
- Node 复用 `src/upstream/ark/`，维护固定提示词、模型输出结构、有限分批及候选整理。按章节／页和文本块边界分批，必要时保留有限上下文重叠；块超过请求预算时拆成有来源映射的子块。完整请求包含提示词与契约的字节数必须计入预算；单个必要请求无法装入预算时明确失败，不偷偷删字段或截断后声称完整。
- 每个抽取字段／关系附原文短引文与 block_id；Node 核对块存在及引文可在对应块定位，页码由块映射获取。文字匹配只证明定位，不证明语义正确；人物归属、关系含义仍须校验及人工确认。不能定位时按已有 unavailable 规则提示，不能伪造证据。文档中的指令只作为待处理内容，不能改变抽取规则或触发工具操作。
- 块内人物使用候选临时 ID 引用，不以姓名作为正式实体 ID。重叠块只消除同一来源定位的重复输出；跨块人物、同名者或任职无法确定归属时保留分开的候选并警告，不自动合并或拼接履历。
- 文本块经固定 JSON Lines 协议逐块传输，单帧 UTF-8 编码后最多 256 KiB（项目默认值，待样本验证）；超过时拆成保持来源映射的子块；原始块及批次缓存只在本任务临时生命周期中存在，受现有临时空间、处理时长和清理规则约束。不把整份解析正文放进单条 IPC 消息、任务表、日志或审计。Node 与 Python 的缓存／临时文件均在任务终止时清理；待确认状态只保留候选和必要短证据。
- 沿用单任务并发、最多 8 批／16 次模型调用（含重试），统一由 Node 计数；解析与抽取共享 15 分钟处理预算。取消或超时停止模型请求并终止对应解析工作，不能由不同层分别重试而突破总预算。
- 不自研 PDF 解析、OCR、通用抽取框架、模型路由系统或图转换器。直接 Docling 仍有 OCR／模型资源和镜像成本，须锁定依赖并验证两种目标平台；不能把移除 Docling Graph 等同于轻量部署保证。

### 本体与证据

跨语言数据采用固定契约与共享 JSON 正反样例（工程审查 D5：已确认 5A），不建设跨语言代码生成流程。新增一份契约说明及共享测试样例，三端仅实现各自职责所需的类型与校验：Python 校验解析文本块的输出形状，Node 校验接口参数、模型抽取候选及引文定位，Rust 对所有入库路径执行最终业务约束（实体存在、关系类型与两端类型、版本、归档和操作 ID）。任何入口均不能绕过 Rust 的入库约束。

正式人物与组织的 `name` 为必填非空字符串；抽取候选缺少名称时标为不可提交，允许用户补充。`telephone`、`email`、`skills`、`alternateName`、`sameAs` 固定为字符串数组，空集合用 `[]`；其他可选单值字段未知时省略，不混用空字符串或 `null`。电话保留字符串，不猜测国家区号。任期日期采用 `YYYY`、`YYYY-MM` 或 `YYYY-MM-DD` 字符串，验证对应精度下的有效日期，不补造月日。校验样例覆盖多值、未知值、非法日期、非法关系端点和未知字段；未知业务字段明确报错，避免静默丢弃。旧网页联系人继续使用原契约，进入图谱时通过专用映射转为新契约，不复用其禁止直接联系方式的限制。

- 业务实体固定为 `Person`、`Organization`；应用生成稳定 ID，不用姓名作为唯一身份。
- 人物与组织采用下方「首版数据契约」的完整字段白名单；不使用“等”作为扩展入口。
- 关系白名单为 `worksFor`、`alumniOf`、`affiliation`、`memberOf`、`colleague`、`spouse`、`parent`、`children`，并校验两端实体类型。[Schema.org Person](https://schema.org/Person)
- 任职记录按组织分别保存职位和时间，使用嵌入式 `OrganizationRole` 信息承载 `roleName`、`startDate`、`endDate`，不新增业务节点类型；不把所有历史职位压成一个当前 `jobTitle`。[OrganizationRole](https://schema.org/OrganizationRole)
- 每段任职各存一条 `worksFor` 关系（工程审查 D4：已确认 4A），拥有稳定关系 ID，职位、任期和证据绑定到该关系。同一个人与同一家组织允许存在多条任职关系，支持职位变化、兼任及离职后重新入职。读取完整履历时查询全部相关关系；图库的邻居遍历仅用于发现关联实体，不能代替完整关系查询，因为它可能按邻居实体去重。
- 日期精度不足时保留原始精度；结束日期缺失不等于仍在职。
- `parent` 按“子女→父母”存储，`children` 作为逆向查询；`spouse`、`colleague` 规范化存一条、双向可查。不因同公司自动创建同事关系。
- 来源、确认状态、审计和版本属于应用元数据，与 Schema.org 业务属性分开保存，不冒充标准属性。

为字段值和关系分别保存证据：来源类型、文件名或网页 URL、文件摘要、短引文、页码、采集时间、确认者。来源定位不精确时明确标记，不将节点定位误当作所有字段均已核实。[Docling Graph 来源机制](https://docling-project.github.io/docling-graph/fundamentals/graph-management/provenance/)

### 首版数据契约（Schema.org 核对后的明确约定）

本节是首版业务数据形状的依据。参考 [Person](https://schema.org/Person)、[Organization](https://schema.org/Organization)、[OrganizationRole](https://schema.org/OrganizationRole) 和 [PropertyValue](https://schema.org/PropertyValue)。Schema.org 定义词汇及可接受的值类型；下述必填规则、数组形式、白名单、图存储方式及元数据是本项目约束，不宣称它们是 Schema.org 的强制要求。仅保存两类业务节点；嵌入式值对象不成为独立图节点。本文示例为内部 JSON 契约，不是 JSON-LD，也不是 Rust 库的直接调用参数。

#### 人物与组织字段白名单

共同字段如下；人物的标准属性为共同字段加两张人物专属字段表，另有下方单列的项目扩展，组织字段为共同字段加 `legalName`、`identifier`。表中逐项列出的字段构成完整白名单；关系属性单独存边，不在人物 properties 中重复保存。

| 共同属性 | 内部类型 | 必填与语义 |
|---|---|---|
| `name` | string | 唯一必填业务字段；正式档案非空，姓名／组织常用名称，不充当唯一身份 |
| `alternateName` | string[] | 别名、英文名、组织简称；未知为 `[]` |
| `description` | string | 可选简介；不使用 `bio` |
| `telephone` | string[] | 电话，可保留区号、分机；未知为 `[]`，不猜测号码所属国家 |
| `email` | string[] | 邮箱地址；未知为 `[]` |
| `address` | string | 可选完整地址文本；首版选用标准允许的 Text，不拆分省市，不引入 PostalAddress 节点 |
| `url` | string | 可选主要主页，合法绝对 HTTP(S) URL |
| `sameAs` | string[] | 能明确指向同一主体的身份页面 URL；普通新闻、搜索结果作为来源保存，不放这里；未知为 `[]` |

| 专属属性 | 所属类型 | 内部类型 | 规则 |
|---|---|---|---|
| `jobTitle` | Person | string | 可选展示职称；有独立来源或人工确认，不代表完整履历或当前任职 |
| `skills` | Person | string[] | 技能文本；未知为 `[]`，不推断熟练度 |
| `legalName` | Organization | string | 可选法定名称；与常用 `name` 分开，不能根据简称猜测 |
| `identifier` | Organization | PropertyValue[] | 外部组织标识；未知为 `[]`，不替代应用 entity_id |

`identifier` 每项固定为 `{"@type":"PropertyValue","propertyID":"标识体系","value":"原始标识字符串"}`。三项均必填，`@type` 固定，另外两项非空；例如 `propertyID=CN-USCC` 表示中国统一社会信用代码（项目约定的体系名称），不能把来源不明的编号猜成信用代码。首版只支持字符串 value，同一体系与值去重；这些编号仅用于匹配建议，不触发自动合并。

完整档案中所有适用的数组字段必须存在，空集合用 `[]`。单值未知时省略，不用空字符串或 null。字符串去除首尾空白；数组去除完全相同的重复项，保留展示文本。人物／组织不能互换专属字段。姓与名只有来源明确区分时才填，不根据中文姓名或姓名顺序猜测；组织电话不自动复制到个人。人物扩充字段和嵌入对象遵守下述约定。组织层级、财产、身高体重、税号及商品交易等字段暂不纳入。

#### 人物扩充字段（2026-09-26）

前版仅 10 个人物属性，不能充分表达简历和人物资料。本次在原有字段上增加以下 21 项，共 31 个人物属性（不含单独存储的关系）。名称和语义依据 [Person](https://schema.org/Person)，对象形状采用标准允许类型中的受限子集。全部为可选业务信息：输入可省略，正式完整档案中的数组归一为 []，不提高最低建档要求。

| 属性 | 内部类型 | 用途与抽取规则 |
|---|---|---|
| `givenName` | string | 名，来源明确时填写 |
| `familyName` | string | 姓，来源明确时填写 |
| `additionalName` | string | 中间名／附加姓名，不与 alternateName 混用 |
| `honorificPrefix` | string | 姓名前称谓，如 Dr.；不自动推出学位 |
| `honorificSuffix` | string | 姓名后称谓，如 PhD；保留原文，不自动推出已核验资质 |
| `birthDate` | string | 出生日期，保留年月日精度，不从年龄反推 |
| `deathDate` | string | 去世日期，适用于历史人物资料，同样保留精度 |
| `gender` | string | 来源明确声明的性别文本，不限制为二元枚举，不从姓名、照片推断 |
| `nationality` | Country[] | 国籍，可多项；不把出生地或居住地当国籍 |
| `birthPlace` | Place | 出生地，不与籍贯、住所混用 |
| `homeLocation` | Place | 居住地点，仅保存明确提供的地点 |
| `workLocation` | Place[] | 工作地点，可多个；不自动等同组织注册地址 |
| `knowsAbout` | string[] | 熟悉的领域／主题，与具体技能 skills 分开，不据此认证专家水平 |
| `knowsLanguage` | string[] | 掌握的语言；能无歧义映射时采用 BCP 47 代码，否则保留原文，不推断熟练度 |
| `award` | string[] | 获奖名称及必要文本限定，使用单数属性名 award |
| `hasOccupation` | Occupation[] | 职业类别，如软件工程师；具体公司、任期和职位仍放 worksFor |
| `hasCredential` | EducationalOccupationalCredential[] | 已获得的学位／职业资质，申请或在读不等于已取得 |
| `contactPoint` | ContactPoint[] | 有明确用途的联系方式，如工作、个人、助理联系渠道 |
| `faxNumber` | string[] | 传真号码，作为文本保留 |
| `image` | string | 已有公开头像 HTTP(S) URL；不保存或从上传文件裁剪头像，不自动下载 |
| `disambiguatingDescription` | string | 用于区分同名人的简短事实描述，不能写推测性身份判断 |

嵌入对象只作为实体 JSON 属性保存，不增加图节点种类，也不建设通用对象建模系统。以下是全部允许的内部字段，未知嵌套字段同样报错；可选字符串未知时省略：

| 类型 | 必填 | 可选 | 约束 |
|---|---|---|---|
| Country | `@type="Country"`、`name:string` | 无 | name 非空，不自行推定国家代码 |
| Place | `@type="Place"`、`name:string` | `address:string` | name 为地点名；address 为明确的地址文本 |
| Occupation | `@type="Occupation"`、`name:string` | `description:string` | 不将岗位要求当作人物经历；不存工资或职位招聘条件 |
| EducationalOccupationalCredential | `@type="EducationalOccupationalCredential"`、`name:string` | `credentialCategory:string`、`educationalLevel:string`、`description:string`、`url:string` | 类别可为学位或证书；层级可为本科、硕士；名称、层级、专业等只根据原文记录 |
| ContactPoint | `@type="ContactPoint"`、`contactType:string`、`telephone:string[]`、`email:string[]` | `url:string` | 电话、邮箱、URL 至少一项有值；contactType 必须来自明确用途，不猜测 |

[Occupation](https://schema.org/Occupation) 用于职业类别，[EducationalOccupationalCredential](https://schema.org/EducationalOccupationalCredential) 用于教育／职业资质，[ContactPoint](https://schema.org/ContactPoint) 用于带用途的联系渠道。资质的学校关系仍使用 alumniOf，不能仅因资质名称出现某学校就认定校友；首版不结构化保存完整教育时间线、授予机构关联和证书有效期，这类有依据的详情保留在资质 description 及证据中。不能把认可机构 recognizedBy 错当作授予机构。

新增日期复用任职日期的精度与日历校验，出生区间整体晚于去世区间时拒绝。对象数组按规范化完整对象去重，不能仅凭 name 合并不同资质或职业记录。所有子字段均要有证据：对象数组的 field_path 指向数组属性，value 保存完整对象，并增加可选 `value_path` 指向其叶子字段（如 educationalLevel）；无 value_path 的证据必须支持整个对象。这样不依赖可变数组下标，也不能用证书名称的证据冒充学历层级证据。

telephone/email 保留无用途的直接联系方式；明确属于人物本人且用途已知时可放 contactPoint，不在两处重复保存同一条已知用途记录。助理渠道仅存 contactPoint 并明确用途，不进入人物本人的电话／邮箱去重键。联系电话查询统一读取这两种来源；按值去重展示时保留用途和证据。

此次扩充同步约束文档抽取模板、预览编辑、Rust 最终校验及共享样例；最低有效档案仍只要求 name。模型不必填满 31 个字段，不为缺失字段补造内容。检索首版继续采用现有关键词／向量接口，不为每个新增属性增加单独接口或索引；向量文本可加入领域、语言、职业、资质与获奖信息，联系方式查询仍走结构化／关键词匹配。

#### 人物项目扩展（用户已确认）

在 31 个标准词汇属性之外，增加以下四项人物业务资料，放在实体顶层 `extensions` 中，与 `properties`、`metadata` 并列。它们是项目自定义字段，不宣称属于 Schema.org，不放入审计元数据，也不新增业务节点或通用自定义字段系统。Organization 不接受此扩展对象。

| 路径 | 类型 | 规则 |
|---|---|---|
| `extensions.nativePlace` | string | 可选非空籍贯文本；按明确原文保存，不由 birthPlace、homeLocation、国籍或姓氏推断 |
| `extensions.hobbies` | string[] | 个人爱好；完整人物档案默认为 []，逐项保存证据并去除完全重复值；不得从职业、skills、knowsAbout 推断 |
| `extensions.maritalStatus` | object | 可选婚姻状态对象，结构为 `{status, asOf?}`，未知时整个省略 |
| `extensions.instantMessaging` | object[] | 多个即时通信账号，完整档案默认为 []；每项固定为 `{platform, accountId, label?}` |

`instantMessaging` 每项的 platform、accountId 为必填非空字符串，label 为可选非空用途说明（如“工作微信”）。platform 使用小写平台标识，满足 `[a-z][a-z0-9_-]*`，微信固定为 `wechat`；平台明确但无预设映射时由人工确认标识，不建设平台注册系统。accountId 去除首尾空白后保留原始大小写和内部字符；不猜测各平台的大小写等价规则。不能使用昵称、二维码图片或手机号推测账号 ID；未能确认真实 ID 时留在候选警告中，不生成账号记录。

同一人物允许多个平台及同平台多个账号。按 `(platform, accountId)` 精确去重，合并证据；相同账号的 label 冲突由用户选择，不覆盖已有用途。不同账号不是冲突，不相互替换；跨人物相同账号只提示检查，不自动合并人物。首版此数组只保存人物本人的账号，助理或其他人的账号不得归到本人名下。label 没有明确依据时省略，不自动标为工作或个人。

每个账号绑定独立证据，field_path 为 `extensions.instantMessaging`，value 为完整账号对象，value_path 可指向 platform、accountId 或 label；沿用嵌入对象的逐字段证据规则。更新时通过 set_extensions 完整替换账号数组，并使用版本检查；字段省略表示不改，[] 表示明确清空。历史证据保留，当前查询仅返回已选账号。此扩展只保存和查询账号，不增加自动加好友、发送消息或二维码识别功能。

`maritalStatus.status` 固定为 `never_married`（未婚）、`married`（已婚）、`divorced`（离异）、`widowed`（丧偶）、`other`（其他明确状态）；“未知／未提供”不能写成未婚，模糊的“单身”也不能直接映射为 never_married。other 的原始含义必须保存在对应短引文或人工证据说明中，展示时一并返回。

`maritalStatus.asOf` 表示该状态在来源中明确对应的日期，允许 YYYY、YYYY-MM、YYYY-MM-DD 并复用日期有效性校验；日期未知时省略。证据的 collected_at／confirmed_at 仍记录采集与确认时间，不能冒充状态生效或适用日期。回答时说明 asOf（如有）及证据时间，不保证旧记录就是今天的状态。

婚姻状态与 spouse 分开保存：已婚可以不知道配偶是谁，没有 spouse 不等于未婚；删除配偶关系也不自动改写状态。同样，不能仅因存在配偶记录而静默设置婚姻状态。新增状态与配偶关系出现明显冲突时，在确认预览及问答中明确提示并要求人工核对，不自动删除关系或覆盖已有值；不同时间的记录不能直接当作同一时刻的矛盾。

四个扩展字段全部沿用字段值证据、人工确认、版本检查、操作 ID 和冲突保留规则。evidence.field_path 允许 `extensions.nativePlace`、`extensions.hobbies`、`extensions.maritalStatus`、`extensions.instantMessaging`；爱好绑定单个值，婚姻状态绑定完整对象，可使用 value_path 指向 status 或 asOf，分别要求证据。未知扩展字段和未知对象子字段明确报错。

人物完整输出必须含 `extensions`，其最小值为 `{"hobbies":[],"instantMessaging":[]}`；创建输入省略时由服务端归一化。编辑使用 `set_extensions`／`unset_extensions`，沿用 set_properties／unset_properties 的部分更新规则：字段省略表示不改，hobbies／instantMessaging 用 [] 清空，nativePlace／maritalStatus 通过 unset 明确删除；maritalStatus 设置时整体替换，不能在改变状态后误留旧日期。扩展字段同步进入抽取候选、预览、保存、查询和共享正反样例，不影响旧 get_contacts 的公开搜索契约。

毕业院校仍通过 alumniOf 关联组织，性别仍使用 gender。alumniOf 本身只表示校友关系；只有明确毕业证据才能回答“毕业于”，不能从校友关系或学校名称推断已毕业、学位或专业。本次不额外增加毕业院校文本字段。

#### 实体标识与元数据

实体固定封装为 `{entity_id, label, properties, metadata}`，Person 额外包含同级 `extensions`：`entity_id` 为应用生成且不可变的字符串 ID，`label` 为 Person 或 Organization，`properties` 只含上述字段。合并只允许同类实体，旧 ID 重定向到保留 ID；人物与组织即使同名也不能合并。组织同样支持查询、保存、归档与恢复，复用已有工具，通过 label 区分。

`metadata` 独立保存：正整数 `version`、UTC 时间 `created_at`／`updated_at`，可选 `archived_at`／`merged_into`；均由服务端维护，客户端不能直接赋值。调用者 userId、operation_id 及历史修改留在审计记录中。向量及其模型、维度、内容版本和索引状态是派生索引数据，不放入 properties，不由用户写入。

#### 关系类型与方向

| relation_type | source → target | 存储与含义 |
|---|---|---|
| `worksFor` | Person → Organization | 每段任职一条，可并存；包括历史任职，查询时必须带任职上下文 |
| `alumniOf` | Person → Organization | 校友关系；不能把仅申请学校或尚未确认的就读记录直接认定为校友 |
| `affiliation` | Person → Organization | 有明确依据的组织关联；不能替代已明确的任职事实 |
| `memberOf` | Person → Organization | 个人会员关系；首版只选用标准中的这一端点组合，不扩展组织间会员关系 |
| `parent` | Person（子女）→ Person（父母） | 只保存此方向 |
| `children` | Person（父母）→ Person（子女） | 输入时交换端点归一为 parent；查询时作为反向视图，不重复存储 |
| `spouse` | Person ↔ Person | 两端 ID 排序后存一条，双向查询 |
| `colleague` | Person ↔ Person | 两端 ID 排序后存一条，双向查询；同公司不自动推出同事 |

所有关系拒绝自关联、错误类型与不存在的端点。除 worksFor 外，同类型规范化端点组合保存一条关系并聚合证据，不推演家庭或组织关系。家庭关系和同事关系必须来自明确原文或人工输入。首版不建设通用时态关系引擎；历史配偶等不能被抹去时间限定后提交为当前 spouse，存在此类材料时提示首版结构不支持，保留在候选警告／简介中待人工处理。

关系封装固定为 `{relation_id, source_id, target_id, relation_type, properties, metadata}`。ID 稳定；metadata 的版本和时间规则同实体，但关系撤销使用 `archived_at`，不使用 merged_into。除 worksFor 外 properties 固定为 `{}`。证据在独立记录中引用关系 ID。

#### 任职、日期与人物职称

worksFor.properties 固定为 `{role: {"@type":"OrganizationRole", roleName?, startDate?, endDate?}}`；role 必须存在，`@type` 固定，三个可选字段均为字符串。公司已知而职位、日期未知时也可存任职关系。每段任职有独立关系 ID，不能以人物与组织组成唯一键。

- `roleName` 是该段任职职位的权威字段；`Person.jobTitle` 是独立的展示职称，不自动双向同步。只有源材料给出不带组织归属的职称时，可以只记录 jobTitle；不得据此虚构组织。
- 履历、组织筛选及“在哪家公司担任什么职位”以关系为准；jobTitle 与任职信息有冲突时提示冲突，不静默选择或覆盖，不拼接成一个职位。
- 日期允许 `YYYY`、`YYYY-MM`、`YYYY-MM-DD`，原样保留精度，这是项目为避免补造日期采用的输入约定。不是完整日期的值不宣称符合严格 JSON-LD Date 输出；首版不实现 JSON-LD 导出。
- 校验日历有效性；把日期解释为其精度覆盖的区间，只在开始区间整体晚于结束区间时拒绝，不能因缺少月日臆断先后。
- 缺少 endDate 不等于在职。worksFor.metadata 增加 `employment_status: current | ended | unknown`，默认 unknown；current 必须有明确“在职／至今”的证据或人工确认，并携带完整日期 `status_as_of`。这是应用元数据，不是 Schema.org 属性。
- current 不允许同时出现 endDate；ended 可缺失具体结束日期。过去已确定结束的日期可以支持 ended；未来结束日期不得被当作已经离职。状态矛盾时需用户修正后提交。
- 回答“当前任职”时说明状态确认日期，不把过去某次 current 记录当作今天仍在职的保证；没有依据时返回任职状态未知。

#### 字段值证据与冲突

复用计划中的证据记录，不新增通用断言引擎。记录固定包含 `evidence_id`、`subject_kind`（entity/relation）、`subject_id`、`field_path`、`value`、`source_type`（file/web/manual）、`collected_at`；正式入库时补充 `confirmed_by`、`confirmed_at`。时间为 UTC 时间戳。`field_path` 指向已允许的 properties 字段，任职状态可指向上述 metadata 字段；关系存在性使用固定路径 `$relation`，其 value 为规范化的类型与端点对象。

数组字段的证据绑定单个实际值，不绑定可变数组下标；identifier 绑定完整 PropertyValue 对象。来源为文件时保存 file_name 和 SHA-256，网页保存 source_url；可选 quote 只保存必要短引文，page 仅在有可靠定位时保存为从 1 开始的正整数。自动抽取值没有可核实的短引文时标记 `locator_status=unavailable`，否则 `located`；manual 使用 `not_applicable`，以操作者确认作为依据，不能伪造引文。

properties 是已选择的展示值，证据记录保留不同来源提出的其他值；比较当前值与证据值即可展示冲突，不另造完整事件溯源系统。单值冲突由用户选择；数组逐值确认保留或删除。手工编辑也追加对应证据，不删除历史来源；读取与问答只把已选值作为事实，对未选冲突明确提示。档案层有来源不等于每个字段均有证据；每个正式入库值及关系存在性都必须绑定至少一条来源或人工确认记录。

编辑采用部分更新：未提供字段表示保持原值，`set_properties` 指定完整替换的单值／数组，`unset_properties` 明确删除可选单值；数组清空用 []。禁止清除 name、同一字段同时 set/unset、未知字段及 null。这些是写工具参数，不属于 Schema.org 属性。

### 去重与修改

跨文件匹配只生成合并建议：电话、邮箱、即时通信账号、姓名与组织等用于排序，不自动合并；共享电话号码也不能作为唯一身份依据。

#### 改名与相同手机号匹配（用户已确认）

- 新记录的姓名与已有档案不同，但本人手机号匹配时，仍生成“可能为同一人”的候选，不以姓名不一致排除。沿用现有导入预览和合并工具，不增加自动身份合并流程。
- 匹配使用电话的派生规范化值，展示与证据保留原始字符串。仅消除明确的格式差异（空格、括号、连字符），只有来源明确给出国家区号时才使用该区号；未知区号不补造，不按尾号或模糊相似号码认定匹配。不同表示之间无法可靠确定等价时不强行匹配。
- 只有明确属于人物本人的手机号才参与该规则；共享总机、助理电话、用途或归属不明的联系方式不能作为本人手机号命中。contactPoint 中符合条件的本人号码同样参与，不能因存储位置不同遗漏。归属判断来自现有来源证据与明确用途，不能仅因号码写在人物档案中就推定其归属。
- 候选展示新旧姓名、匹配号码、各自来源和采集时间，并展示其他支持或冲突证据：本人邮箱、微信账号、任职经历、明确的改名说明。来源给出有效时间时一并展示，采集时间不冒充号码持有时间；号码回收、多人共用和来源过期均可能导致误匹配。不输出未经校准的概率百分比，不设置手机号全局唯一约束。
- 用户明确确认“同一人且新姓名为当前姓名”后，保留选定档案的稳定 entity_id，将新姓名写入 name，旧的有效姓名去重加入 alternateName，并保存旧名来源和改名确认记录。alternateName 不区分别名、英文名和曾用名；只有证据明确时才能称为曾用名，不根据别名存在推断改名或改名日期。
- 如果用户只确认同一人，未确认哪个姓名应作为当前姓名，则保留现有 name，由用户选择其他姓名是否加入 alternateName；不能按文件上传顺序、采集时间或“较新的来源”自动切换当前姓名。纠正录入错误不等于改名，错误姓名不自动加入 alternateName。
- 新记录尚为候选时直接合并到既有档案，不另建人物；若两个正式档案已经存在，则复用合并事务，保留选定目标 ID，另一 ID 重定向，关系、履历及来源按既有规则保留。姓名更新、别名补充、证据和合并结果必须同事务提交，沿用版本检查与 operation_id 幂等规则。
- 无法确认时不合并：未提交候选可继续待确认或明确选择新建／跳过；已经存在的两个档案保持独立。同一匹配规则也不能绕过归档与恢复约束。

验收补充：不同姓名且同本人手机号会给出候选；共享／助理号码不触发本人手机号规则；区号未知与尾号相同不误匹配；号码被他人使用时可以保留两个独立档案；确认改名后新旧姓名均能检索到同一稳定 ID；未确认当前姓名时不自动改名；纠错不生成曾用名；重复提交不重复创建别名、关系或人物。


#### 通用合并与归档规则

确认时为每个候选明确选择“新建、合并至已有档案、跳过”。冲突字段保留各自证据，由用户选择展示值。合并事务重定向关系和来源，旧 ID 保留重定向。任职关系不以“人物、组织、关系类型”作为唯一键，也不凭职位相同或日期缺失自动判重；同一来源重复重放沿用原关系 ID，不重复插入，跨来源疑似重复任职保留到用户明确确认合并。其他关系按其已定义的方向与对称规则去重，并保留全部来源。编辑使用版本检查，避免覆盖其他用户的新修改。

联系人删除定义为共享联系人库中的归档（工程审查 D3：已确认 3A），采用软删除，同时退出档案查询、关系遍历、向量召回及联系人问答；审计记录和已知来源映射保留。后续同步命中这些映射时，仍关联已归档档案，不自动恢复，也不另建一条可见档案。映射先解析合并重定向，再检查目标档案的归档状态。

用户可通过现有 `save_contact` 的明确恢复动作恢复档案，遵守版本检查与操作 ID 规则；后台同步不得执行恢复。归档只作用于已识别档案及其已知来源，不按姓名封禁同名人，也不承诺识别所有未知来源中的同一人。既有 `get_contacts` 是公开网页搜索，仍可能返回该人物；新联系人库查询和问答不返回归档档案。这一区别必须写入工具说明。

### 写入重试与结果确认（工程审查 D2：已确认 2A）

所有联系人写操作携带稳定的 `operation_id`，由调用方为一次业务操作生成并在重试时复用；文件导入确认使用带操作类型前缀的导入任务 ID。读取操作不需要操作 ID。

Rust 在图数据库中用一张操作结果表保存操作 ID、操作类型、调用者、规范化请求摘要和成功结果，与业务修改在同一事务中提交。重复请求先检查操作记录，再检查业务版本：同一 ID、同一调用者且内容相同，返回原成功结果；同一 ID 被不同调用者使用或内容不同，返回明确冲突，不再次执行。事务失败则业务修改与操作结果一起回滚。

响应丢失或进程退出后，只能使用原操作 ID 和原请求重试；不能生成新 ID 盲目重放。MCP 工具参数和说明明确这一约定。测试须覆盖提交成功后响应丢失、重启后重试、相同 ID 不同内容及事务回滚，验证不会重复创建联系人、关系或执行合并。

## 3. 导入流程与公开接口

### 文件处理

1. `POST /contact-files` 接收单文件 multipart 上传，复用 Bearer、Host 和 Origin 校验；CLI 支持逐文件批量上传。
2. 校验实际格式、体积、页数及图片解码资源上限；拒绝损坏、加密 PDF 和伪装文件，返回 `file_id`。
3. MCP 发起异步导入。Python 用 Docling 解析本地文件并返回带来源定位的文本块；Node 按固定联系人契约组织批次，复用现有方舟客户端抽取候选，执行结构校验及引文核对。整个解析与抽取流程共用单任务超时、调用预算和取消信号，不在 Python 中另建模型客户端。
4. 抽取结果返回字段、关系、短证据、告警和疑似重复档案；支持一份文件包含多人。文件导入不套用现有“只允许关键岗位、禁止联系方式”的网页规则。
5. 完成或失败后立即清除原件、页面图及完整解析产物；尚未发起抽取的上传文件默认一小时过期，已排队文件不适用此过期规则。成功路径先持久化待确认候选和必要短证据，再清理原件；启动时清理崩溃遗留文件。关闭 Docling 调试导出及模型请求正文日志。
6. 用户确认后，档案、关系、证据和提交状态在同一图数据库事务中落库；重复确认返回原结果。
7. 向量异步生成；失败不撤销已经确认的联系人，明确显示索引状态并支持重试。

任务状态采用 `queued → processing → ready_for_review → committed`，另有 `failed`、`cancelled`。中断任务标为失败，重新抽取需重新上传文件；已保存的待确认结果不受影响。

### 资源边界（工程审查 D7：已确认 7A）

下列数值为首版可配置默认值，不是已测得的容量承诺：

| 边界 | 默认行为 |
|---|---|
| 未完成文件数量 | 上传中、待提交、排队及处理中合计最多 10 个；接收文件前原子预留名额，满额返回 HTTP 429 及 `CAPACITY_FULL`，不接收文件正文 |
| 名额释放 | 上传失败、未提交过期、取消、处理失败或待确认结果持久化且临时文件清理完成后释放；各路径保证只释放一次 |
| 抽取并发 | 1；批量 CLI 按顺序上传，达到容量上限即列出已接收文件 ID 和未上传清单后结束，非零退出，不自动等待或续传 |
| 处理时间 | 单任务从开始处理起最多 15 分钟；排队时间单独显示，不算处理时长 |
| 图像资源 | 每张输入图片及每个 PDF 渲染页最多 2500 万像素；尽早通过尺寸信息检查，避免先完整解码再判断 |
| 临时产物 | 每个处理任务最多 1 GB；生成时检查配额，达到上限终止处理并清理 |
| 抽取调用 | 每文档最多 8 批、总计 16 次模型请求（含重试）；完整请求字节预算复用现有配置 |

超时、像素或临时空间超限均明确失败，不把中断结果伪装为完成。仅模型分批预算耗尽时，可以返回已校验的部分候选供确认，但必须报告已处理／未处理范围与警告；候选为空则返回明确空结果及原因。容量预留及清理状态由本实例维护；启动清理遗留文件、终结中断任务后重新开放上传。名额不能因一次取消和随后的退出回调而重复释放。

```text
上传请求 -> 预留名额 -> 校验并临时保存 -> 排队 -> Python解析 + Node抽取
    |满额         |失败/过期                  |失败/超时/取消
    v             +------------- 清理并释放 <-+
   429                                      |
                                            +-> 保存待确认候选
                                                 -> 清理并释放
                                                 -> 用户确认
                                                 -> 图事务 + 操作结果
                                                 -> 向量生成
```

文档与模型网络操作不得持有图数据库写事务。首版不增加外部队列、自动扩容、任务优先级或自动续传；通过固定样本记录解析耗时、峰值内存、临时空间和调用次数，验证默认值是否适合发布镜像。

## 4. 向量问答、迁移与实施顺序

### 向量和问答

- 在 `.env` 与 `.env.example` 中预留独立的向量配置，调用方舟文本向量接口；部署时验证接口和返回维度，不猜测可用模型。
  - `ARK_EMBEDDING_API_URL`：完整嵌入请求 URL，示例为 `https://ark.cn-beijing.volces.com/api/v3/embeddings`，可按实际部署修改。
  - `ARK_EMBEDDING_MODEL`：支持文本嵌入的模型或端点 ID，默认留空，由部署者填写。
  - `ARK_EMBEDDING_CREDENTIAL`：嵌入接口凭据，默认留空，由部署者填写；不隐式回退到聊天配置。
  - 本次仅保存配置项；实现向量功能时接入 `src/config.ts` 的白名单、校验和调用方。未配置完整时向量能力不可用，关键词检索仍可用，不影响现有服务启动。配置完整后校验 HTTPS URL，并通过实际调用确认模型可用及返回维度。[官方 API](https://api.volcengine.com/api-docs/view?action=Embeddings&serviceCode=ark&version=2024-01-01)
- 对确认后的档案及履历生成向量，记录模型标识、维度和内容版本。修改或合并后立即使旧向量失效，再异步重建；不同模型的向量不得混查。
- 首版调用 Rust 库的向量查询，结合关键词和结构化过滤，以排名融合返回候选；最多扩展两跳相关关系，并限制返回数量。
- 问答将自然语言转为受校验的查询条件，执行后再整理事实。模型不能执行任意 SQL，也不能将语义相似度转为关系事实。
- 同名歧义返回候选供选择；无证据或存在冲突时明确说明。直接关系问题优先用确定性模板回答，复杂问题引用检索到的事实和短证据。
- 嵌入失败时明确降级到关键词查询；生成失败时返回结构化事实，不伪造答案。

### 旧数据迁移与持续同步

- 旧搜索快照保留，按快照 ID 和条目建立幂等来源映射，回填图谱。
- 仅将同一查询范围内完全相同的旧联系人键视为同一旧记录；跨查询、跨来源的同名者保留待合并状态。
- 保留发布时间、首次／末次发现时间及历史证据含义，不将“最新搜索未出现”改写为“已经离职”。
- 直接复用永久追加的搜索快照作为同步来源，不新增同步事件表。Node 按递增 `snapshot_id` 分批读取；Rust 在同一图数据库事务中写入该批档案、来源映射及最后完成的快照 ID。响应丢失时重新读取图数据库的同步进度，已处理来源不重复创建。事务失败不推进进度，失败批次保留待重试；图服务短暂失败不破坏旧查询。旧数据回填与持续同步使用同一条处理路径。
- 人工确认的档案值不会被后续搜索静默覆盖；新增搜索结果作为新的来源断言保存。

### 交付阶段

1. **图谱基础**：锁定 Rust 库版本及依赖，完成真实 API、事务回滚、持久化、向量查询和进程协议验证；通过后建设档案与证据仓储。
2. **联系人管理**：实现 CRUD、关系、合并、审计、旧数据回填和同步。
3. **文件导入**：完成上传 CLI、Python 解析、Node 联系人抽取、临时文件清理、预览确认和幂等提交。
4. **检索问答**：接入嵌入服务、混合检索、事实查询和来源回答。
5. **部署验收**：更新现有 Dockerfile 和 `.github/workflows/publish-image.yml`，继续通过版本标签发布 GHCR 镜像，保留已有 `linux/amd64`、`linux/arm64` 两个平台；Rust 二进制和 Python/OCR 运行环境随镜像交付，不增加独立发布系统。固定依赖与模型资源版本，在各目标平台验证图 API、文档解析和非 root 临时目录读写。上传 CLI 随当前 Node 项目交付，文档给出构建后调用方式，不另发独立二进制。保持单实例运行，统一管理子进程生命周期。

新功能通过配置开关启用。迁移先备份并支持 dry-run；关闭功能开关可恢复旧工具路径，同时保留新图数据库以便修复，不直接删除新数据。

### 模型质量验收（工程审查 D6：已确认 6A）

使用 12 份固定合成文档：4 份文字 PDF、4 份扫描简历 PDF、4 份 JPG/PNG 名片，覆盖中英文、多人、多段任职、多联系方式、缺失字段与不可辨认内容。样本及人工核验标注作为测试资产保留，不使用真实个人资料；生产环境不保存用户原件的规则不受测试样本影响。标注记录字段值、人物与组织归属、任职、来源页码和必要短引文，并区别清晰可辨字段与应提示不确定的内容。

对未经人工校正的抽取结果计算清晰字段的微平均准确率（正确输出字段数／全部输出字段数）至少 95%、召回率（正确输出字段数／全部应提取字段数）至少 90%。在固定的字段匹配规则下计分：电话保留数字、区号和分机含义，不擅自补全；姓名、组织和职位仅忽略约定的空白及 Unicode 表示差异；日期须保留标注精度。OCR 错误不能通过宽松匹配被当作正确。不可辨认内容应缺省并报告不确定，不允许猜测后计入成功。

另设 20 个固定查询用例：10 个语义检索、10 个问答。检索至少 9 个用例的目标联系人出现在前五名；问答覆盖直接关系、多段任职、同名澄清、无证据、冲突以及文档中夹带指令的场景。全部问答用例必须满足标注的回答／澄清／证据不足行为，不允许通过一律拒答过关；不得出现伪造关系或引用。引用须对应实际检索到的事实，且短证据支持该事实，不能只校验引用 ID 存在。

不建设评测平台；使用普通测试脚本读取样例、调用真实服务并输出逐项结果、总体指标和失败案例。初版以人工标注为基准；首次合格运行记录 Docling/OCR 版本与配置、模型／端点标识、提示词与抽取契约版本、样本版本和指标作为后续比较基线。相关模型、提示词、抽取或检索流程变更时运行真实质量评测；普通修改只运行确定性测试。合成样本上的通过结论不外推为所有输入的准确率承诺。
