# 企业公开人物发现增强设计

日期：2026-10-15。基准：`main / f9e38a4`。状态：实现与文档已补齐；Rust 编译和实际 Store 测试尚未验证，完整验收未完成，未真实调用。本轮仅本地集成，不推送、不发布。

## 1. 目标与范围

增强现有 `discover_contacts(source="web")`：围绕某家企业，从新闻、公众号、企业文章、会议和技术成果中尽可能发现公开职业人物，而不是只找高管或七产品相关负责人。

普通员工、技术专家、项目人员以及职位不完整的人物都可以成为结果；销售相关性留给后续查询或人工判断，不作为发现门槛。

复用现有豆包搜索、Ark、SQLite `contact_query_snapshots`、图谱 `sync_snapshots` 和 `contact_claims`。不新增平台、MCP 工具、数据库表、数据供应商、人物评分、部门分类体系、七产品联动、持续监测或爬虫。Zoho 查询、全量返回、Owner、隐私和同步语义不变。

本轮先做好一次有预算的企业发现；不进行逐人物递归搜索，不自动调用 QCC 增加主体查询成本，不获取电话、邮箱、微信或私人生活资料。不能承诺全员覆盖。

## 2. 当前限制与实际依赖

## 3. 搜索：围绕人物出现的材料

保留 `query`、`region_hint` 和 `source`。默认四组，每组十条搜索结果，含 URL 和可取得正文：

1. 企业官网、新闻、公众号、人物专访、团队、员工故事。
2. 会议、论坛、展会、协会、演讲、嘉宾、技术分享。
3. 项目、研发、技术文章、论文、专利、成果、获奖。
4. 企业活动、员工代表、培训、竞赛、部门、供应商或客户交流。

不把某产品或质量部门作为固定关键词。第四组的供应商/客户活动用于发现材料，不把其他公司的代表收为本企业员工。

只读取本地已有 `ProfileRepository`：查询词唯一精确匹配缓存法定名称时，复用其法定名称、已确认简称和官网域名；简称按稳定顺序轮换到四组查询，不增加组数。不凭删除地域、公司后缀或 LLM 猜测生成简称。缓存不匹配或有歧义时仅按用户原词搜索，返回主体未完全确认警告，候选不得因查询词自动获得法定主体确认。

外部文章中可提取原文企业名称；只有已有主体资料和材料共同支持时，才映射到法定名称。仅品牌同名、集团/子公司或简称有歧义时保留原文和待核实，不把来源中其他公司静默归到用户输入公司。

## 4. 材料与 LLM 抽取

### 4.1 不再只保留文章开头

对搜索实际返回的标题、摘要、正文做精确重复去重，再沿段落切成连续片段；超长段落按 Unicode 安全边界切分，相邻片段保留边界上下文。每个片段携带页 URL、页内片段编号和原文范围。

以现有 `ARK_REQUEST_MAX_BYTES` 对最终序列化请求测量大小，顺序装入能容纳的片段；超限就开下一批，而不是压缩成仅文章开头。跨查询轮换处理页面，避免一个长页面占用全部批次。优先复用已有 UTF-8 测量方法，不复用七产品关键词打分或复杂证据优选器。

每段都进入待处理序列；在调用或时间预算内处理。未处理片段的数量和页面 URL 进入快照覆盖记录与警告，不能报告为“没有人”。不保存完整网页正文，不建设续跑队列；后续刷新重新检索。这里的完整性只针对本次搜索返回材料，不针对整篇网站或全网。

搜索仅返回摘要时允许提取有证据的线索，并说明未取得正文；图片里的名单本轮不做 OCR，不绕过登录、付费或公众号访问限制。

### 4.2 抽取信息

LLM 输出姓名、原文公司名、原文职位（可为空）、短证据、对应来源片段及企业关系判断。不输出五类 `roleCategory`；来源的发布方、URL 和时间取自输入，不让模型编造。

关系判断只保留两个值，不建立人物分类体系：

- `employment_evidence`：原文明确表示任职，例如“某公司工程师张某”“某公司员工李某”；职位可以未知。它只表示原文有任职证据，不表示当前在职、购买角色或人工核实。
- `unverified`：有与企业相关的职业线索，但无法确认任职或主体，例如公司代表、专利发明人、外部活动归属不完整。不得创建确定任职边。

已明确属于记者、客户代表、合作伙伴或其他公司的人员不作为本企业候选。仅共现且没有可说明的职业关联也不收。只出现“张工”等不完整称谓时保留原文称谓并在警告中说明，不补全姓名、不拿它与实名人物自动合并。

LLM 负责理解段落中的身份关系；代码仅负责边界验证：来源/片段必须属于输入，姓名、非空职位及引用必须能在该片段及其边界上下文定位，企业名映射只能使用已提供身份依据。不能通过姓名、公司、职位在整页任意位置共现就认定任职。

短证据不足以解释归属、不同身份冲突或别名不确定时，降为 `unverified`；不能为了召回放过虚构姓名、URL 或职位。网页指令一律作为资料，不允许改变工具、预算和系统规则。

## 5. 结果与缓存：观察不等于独立人数

### 5.1 最小字段调整

保留现有顶层 `companies`、`warnings`、`collected_at`、可选 `zoho`，以及公司内 `contacts`、`historical_contacts`。网页人物记录扩展为：

```ts
type WebPersonObservation = {
  name: string;
  title: string | null;
  source_url: string;
  published_at: string | null;
  affiliation_status?: 'employment_evidence' | 'unverified';
  evidence_quote?: string;
};
```

新增记录必须有归属状态和可定位短证据；旧记录可以缺少新字段。职位未知使用 `null`，不把“待核实”“代表”写成虚构职位。不把事件日期、发布时间当成任职起止日期。

引用在内存中对原文校验后，移除电话、邮箱和账号内容再保存/展示，沿用 URL 隐私净化，不通过新增证据字段泄露原来不返回的联系方式。没有可安全保留的身份短证据则不返回该观察，并说明验证失败。

### 5.2 保留多来源，不凭同名合并

完全重复的公司原文名、姓名、职位、来源 URL、引用和归属判断可去重；同一姓名不同页面的依据要保留。跨页面同名、同公司同名都不自动认定同一人，必要时提示可能重复。

`contacts` 表示最新发现快照中的观察，不表示现任人员；`historical_contacts` 表示只在较早发现快照出现的观察，不表示已离职。实际报道年份另看 `published_at`，不能把“本次搜到旧报道”称为最新任职。

企业分组规则：已由主体资料与原文共同确认的名称映射可归到同一法定名称；未确认映射的原文公司名按 NFKC、去首尾空白和折叠空白后的精确名称分别成组，不通过相同品牌、删除公司后缀或集团关系合组。分组只是展示归类，不据此合并人物。

同时移除人物 `.max(10)`、历史 `.slice(0,10)`、公司数组 `.max(3)`，以及服务中的 `companies.length >= 3` 跳过与历史投影的三组停止条件。四组及以上有证据的名称分组同样完整保存和分页，不把解除人数上限误写成保留三组截断。当前与历史按完整观察身份比较，不覆盖其他来源的依据。

### 5.3 网页分页，不限制发现人数

增加 `web_offset`（默认 0）、`web_limit`（默认 50、范围 1–100）和可选 `web_snapshot_id`（正安全整数，复用现有快照 ID），以及返回的：

```ts
web_page: { snapshot_id: number; offset: number; limit: number; total: number; next_offset: number | null }
```

按公司规范化名称、当前观察优先于历史观察、再按规范化姓名/职位、来源 URL、引用和归属状态稳定排序（空职位按空字符串排序），形成序列后切页并重新分组；`total` 是网页观察条数，不宣称为独立人数。人物和公司分组旧上限取消；本次已接受观察先全部入快照，再从快照分页。翻页不得重新调用搜索或 Ark。

不传 `web_snapshot_id` 时只允许 `web_offset=0`，沿用新鲜缓存/刷新/旧缓存回退流程，并返回本次实际使用的 `snapshot_id`，包括空结果和旧缓存回退结果。后续页必须携带该 ID；第 0 页也可以携带 ID 重读。带 ID 的调用只读取与当前规范化查询及地域缓存键一致的既有快照，并将历史观察限定为 `snapshot_id <= 绑定ID`：绑定行是本次投影的主快照，不能重新选择最新行。随后出现的新快照不改变该次分页的 total、当前/历史分组或顺序。

缺少续页 ID、ID 不存在或查询/地域不匹配时，返回明确的网页分页错误并提示从第 0 页重新发起，不自动换快照、不调用搜索或 Ark。30 天仍是自动缓存新鲜期，不是已保存资料的读取期限；绑定 ID 超过 30 天仍可读取，但保留“超过 30 天的历史资料”警告，不能因翻页刷新采集时间或当成新鲜缓存。旧缓存回退同样返回所用 ID 并可固定续页，不新增读取过期机制。并发首次刷新继续复用 singleflight。本轮不增加刷新参数、不透明游标或新表；快照 ID 只用于结构化翻页，不在普通阅读界面堆叠内部 ID。

`source=all` 的分页只作用于网页部分，Zoho 仍保留原有实时读取行为；客户端继续翻网页时使用 `source=web`，不重复读取全部 CRM。`source=zoho` 不接收网页分页参数（含 web_snapshot_id）。默认字段名不变不代表结构完全不变：`title` 可空、新字段和网页分页都需要同时更新输出 Schema、渲染与 skill。

### 5.4 三十天缓存和升级

快照 JSON 增加可选 `coverage`：`version:2`、`total_pages`、`total_chunks`、`processed_chunks`、`pending_pages`（未完全处理页 URL）、`complete`。网页响应新增 `web_coverage` 返回这份覆盖记录；旧缓存回退时为 `null`，纯 Zoho 不返回该字段。页面 URL 展示同样经过隐私净化。`complete` 仅表示四组搜索和返回材料处理均完成，不表示覆盖企业全部员工。

旧快照照常读取，不修改或删除旧行；但缺少 `coverage.version=2` 时，不作为新版发现的有效新鲜缓存，首次调用需尝试新版刷新。缓存键仍按原查询与地域，避免同源映射全体变化。新版刷新失败时可回退旧缓存，明确“旧发现规则的历史资料，尚未完成增强搜索”，不能假装本轮成功。新鲜新版快照继续复用 30 天；不因打开页面而重复计费。

## 6. 图谱同步：只做必要适配

开关、初始化备份、同步游标、归档保护和幂等保留，不新增自动入库开关或表。

| 新版观察 | 图谱保存 |
| --- | --- |
| 明确任职、职位明确 | Person + Organization + `worksFor`；保留职位和网页短证据 |
| 明确任职、职位未知 | Person + Organization + `worksFor`，不填虚构 `jobTitle/roleName` |
| 企业职业关联待核实 | Person + 候选 Organization + 现有 `contact_claims` 中待核实任职线索；不生成正式边，不把未确认职位写成确定字段 |
| 明确是外部人员/无职业关联 | 不作为本企业观察同步 |

新建网页任职边的 `employment_status` 仍为 `unknown`，不因最新搜索或文章日期标成“已核实当前在职”。如果原文明确写“曾任”，短证据和警告保留其历史限定，不推断离职时间。旧边不自动迁移、不自动改写。

扩展 `claims.rs` 的现有无 `import_id` 来源保护，只有 `source_type=web` 且包含真实快照编号、来源 URL、短证据的 `worksFor` 待核实线索可由快照同步写入；校验对应主体、目标机构、字段、值和 2048 字节限制。不得取消现有 Zoho/file/text 来源限制，也不伪造导入任务。

线索 `value_json` 必须使用现有审核入口的完整包裹形状，不将 role 放到顶层：

```json
{
  "properties": {"role": {"@type": "OrganizationRole"}},
  "metadata": {"employment_status": "unknown"}
}
```

有原文职位才在 properties.role 加 roleName。使用现有人工审核接口，首次确认提供确认说明但不需要 corrected_value 修补结构；确认后能从人物档案回读关系。拒绝不生成正式边，重复处理沿用现有状态与幂等规则，不由同步自动确认。

本轮只验收人物侧 `get_contact(person_id)` 的证据、待核实线索及审核后关系回读；不新增机构侧入向线索反查、不修改图谱 UI 或读取规则。现有正式任职关系的机构侧行为保持，不把它扩展为待核实线索的双向回读承诺。

身份继续通过现有 source_mapping 保守处理。所有新版观察（包括明确任职）按查询、原文公司名、来源 URL、姓名及引用生成稳定观察键；不同页面不因同名、同公司、同职位自动合并。旧格式仅沿用原有身份键，新版不按旧姓名键自动认领旧人物；已存在同一来源观察的映射才复用目标，并解析其人工合并/归档结果。相同观察重查不增人物或线索；不同来源保留独立观察，后续人工合并沿用现有能力，不在本轮建设跨文章身份评分。已拒绝/确认线索不自动重开，归档人物不自动恢复。

新版 TS 传递的扩展字段必须由匹配版本的 Rust 接收。旧快照缺新字段仍可同步，沿用旧格式兼容分支，但在展示中标为旧规则资料，不额外宣称重新核实。

保持现有 256 KiB 图谱帧保护和按快照批次拆分。不扩展内部传输协议：单个快照仍超限时，全部资料已保存在 Node 快照，可分页读取；同步明确记录 `SNAPSHOT_FRAME_TOO_LARGE`，不声称已经入图、不回滚查询结果、不推进越过失败游标。该限制在真实验收中单独检查，不能因取消十人上限而忽略。后续若实际触发，再单独设计单快照分片，不预建续传协议。

## 7. 调用和失败边界

仍为同步发现，不增加任务队列。使用现有 CallBudget 和配置：本功能每次最多 8 次豆包、8 次 Ark、16 次总调用，并分别取不超过部署现有 `MAX_SEARCH_CALLS`、`MAX_ARK_CALLS`、`MAX_TOTAL_UPSTREAM_CALLS` 的值，重试也计数；为抽取保留最多 2 次调用。四组搜索各失败重试一次；每个抽取批次失败最多重试一次，不回放所有已成功批次。

单次新鲜发现墙钟上限 120 秒，向 fetch 和批处理传递 AbortSignal，停止后续派发；搜索最多 2 并发，抽取批次顺序执行，不新增并行调度器。静态预算是上线前的保护值，不是覆盖或完成时长承诺，也不新增用户配置项。

- 部分搜索/抽取失败、预算耗尽或超时：保存已有有效观察和覆盖记录，返回警告及尚未处理范围；下一次命中新快照不再自动重跑。
- 已成功检查全部可得材料但无人：返回空结果，不能说该公司没有员工。
- 没有任何成功抽取批次，且存在未处理材料：不保存成新鲜空快照；有旧缓存则明确回退，否则按现有工具失败返回。
- 模型编造字段、跨页面拼凑依据：逐条拒绝非法候选，计数警告；整个批次无法解析则算批次失败。
- 持久化失败：明确失败，不能回报“已保存”。图谱异步失败不抹去查询结果，使用现有错误报告；响应不承诺“已入图”，须经图谱回读核实。

日志只记录查询/批次标识、耗时、页/片段/候选/通过/降级/拒绝数量和拒绝原因码，不记录完整文章、原始模型输出、姓名清单或凭证。不建设日志平台。

## 8. 验收与交付边界

1. 普通工程师、行政/运营人员、技术专家、无职位人物不再因部门或职级被删除。
