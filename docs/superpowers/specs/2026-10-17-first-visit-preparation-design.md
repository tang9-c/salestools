# 首次拜访准备：功能设计与接口衔接

日期：2026-10-17。状态：设计方案，未实施。执行顺序：持续研究 → 产品销售场景专题 → 本阶段 → 单产品企业比较。

前置：[第一阶段实施方案](../plans/2026-10-17-continuous-company-research.md)、[产品销售场景专题](2026-10-17-product-sales-scenario-design.md)。本阶段只定义功能和接口，不提前拆解代码任务。

## 1. 定位与输入

服务首次拜访前的背景了解和需求探索。最低输入是已确认企业的 legal_name/credit_code；也可提供已有 dossier_id，二者互斥。名称不明确先走画像确认，不通过名称猜测法人。可选 products（七产品中一项或多项）、attendee_roles（岗位）、meeting_date（ISO 日期，仅作背景，不创建提醒）。未指定产品时按已有研究中最相关的场景组织问题，不轮流推销七款产品。

输出一份统一简报：背景、相关工程场景和软件线索、切入假设、访谈问题、建议接触岗位和待核实事项。事实、强线索、假设明确标识。没有人员资料仍可生成；仅凭 CRM Owner 或职位不能确定决策权。

沿用团队共享，记录创建者及取消者。只生成内部准备材料，不向客户发消息、不写 CRM、不制作完整商机推进计划。

## 2. 资料判定与自动补查

先用第一阶段最小单产品读取接口固定资料版本，再由本阶段实现的充分度投影与 freshness-policy@1 判断。判断时间为任务接受时的 assessed_at；不是不断变化的“现在”。

补查触发条件：没有研究档案；请求产品未覆盖；缺少可归属于目标企业的业务/工程场景；支撑关键判断的资料已过复查周期；存在影响本次主题的未处理冲突/技术读取缺口。缺少人员名单本身不触发付费研究。七产品默认扫描时，未发现相关场景的产品不能一律当作必须补齐的缺口。

复查周期沿第一阶段：招聘、软件/项目线索 30 天，基础业务与工程场景 180 天。按每条证据最后成功复查时间计算，不能用报告生成时间刷新旧资料。日期未知或未来日期不能支持“当前使用”；若它是关键判断唯一依据，标 unknown 并列补查。公开资料查不到结果时可完成研究但仍有知识缺口，不无限重试。

每份简报最多自动创建一个研究 run：无档案用 initial；已有档案选择覆盖不足的产品，用 company_research 模板 refresh。只补本次需要的范围，不强制生成专题。研究和简报生成使用各自显式预算，状态分别显示；研究沿第一阶段标准预算，简报模型至多2次（含一次重试）、生成阶段120秒，不追加第二轮研究任务。

企业已有活跃研究时，简报进入 waiting_research 并跟随该任务；任务结束后重读资料并生成。即使该研究范围不完全匹配，也不再自动追加研究，输出不足的简报并说明缺口。研究队满、被拒绝、失败或取消时使用已有可靠资料生成 partial；完全没有可用背景事实时只给已确认主体与中立问题，标明“背景研究未完成”，不能伪装成完整简报。

等待已有任务最多20分钟，超时生成已有资料可支持的 partial，不取消他人研究。自动创建的研究一旦排队即消耗本次一次额度；operation_id 从 brief_id 派生，崩溃重放不得再次收费创建。研究前身份缓存过期时提示先刷新画像，本简报以已有资料降级，不绕过主体确认。

## 3. 简报结构与证据

固定顺序：

1. 企业背景速读：主要产品、业务和研究时间。
2. 值得了解的工程场景：现有工作方式与证据，不预设痛点。
3. 软件使用线索：区分直接证据、招聘要求、个人技能、项目及供应商线索。
4. 切入假设：可复用已存在的专题路径，注明其版本；没有专题也能依据事实提出待验证问题，不自动生成另一个专题。
5. 现场问题：默认最多10个，优先会影响理解的开放式问题；按参会岗位调整深度，不把未经证实的假设作为提问前提。
6. 人员与岗位：已知人员和建议寻找岗位分开；保留任职状态与日期，不输出私人电话邮箱。
7. 未知事项与准备限制：来源失败、过时、范围未覆盖及建议下一步。

例如“目前机械设计主要使用哪些工具？”可由 Creo 技能线索启发；不能改写成“你们已经使用 Creo，为什么不换系统？”。不向模型传入无关个人属性，原文中带联系方式时先做字段白名单和摘录审查。

事实引用固定版本的 claim/evidence ID，人员资料引用生成时的图谱实体/关系版本快照。需要实时 CRM 读取才能获取的信息不自动查取：本阶段复用已入库 CRM 来源图谱资料，注明其来源时间。无已确认公司关联时只给岗位建议，不能把同名人物接上。

生成后不可变。研究后续更新不会修改旧简报；重新生成创建新 brief_id，显式 parent_brief_id 可追踪同次准备的修订。

## 4. 接口、任务与存储

| MCP 工具 | 参数与行为 |
| --- | --- |
| prepare_company_visit | 企业标识、可选 products/attendee_roles/meeting_date/parent_brief_id、operation_id；返回 brief_id/status、是否需要补查及原因 |
| get_company_visit | brief_id；返回状态或统一简报、资料版本、coverage、warnings；读不补查 |
| get_company_visit_evidence | brief_id、可选 section、offset=0、limit=10（1–20）；固定快照分页，不访问外部 |
| cancel_company_visit | brief_id；幂等取消，记录认证 actor；不自动取消共享研究 run |

新增 company_visit_briefs 表：brief_id、parent_brief_id、actor、operation_id、request_hash、request_json、status、research_run_id、research_dispatched（0/1）、assessed_at、input_refs_json、result_json、error_code、created_at/finished_at。UNIQUE(actor,operation_id)。输入资料小型证据快照、引用闭包和渲染结构写入 result_json；上限2MiB，超出按完整证据组省略并标 partial，不输出孤立引用。

状态：queued/waiting_research/generating/completed/partial/failed/cancelled。共享取消仅影响简报；已经创建的共享研究可继续供团队使用，取消回执说明该行为。首版生成并发1，待处理上限20，每用户活跃最多3；属于简报自己的额度，底层研究另受原限制。相同 operation_id 相同输入回放，不同输入冲突。parent_brief 必须同一企业。

普通期限到达保留可用简报为 partial；没有任何可用输出或存储失败为 failed。模型生成失败采用固定中立提问模板和已验证背景生成 partial；不把失败模型文本返回用户。服务重启将未结束简报标 failed/PROCESS_RESTARTED，不自动补发研究；迟到结果不得覆盖取消/失败状态。已有研究的重启恢复独立遵循第一阶段规则。

首屏不返回整份证据库。引用、章节和 schema 均由服务端校验，用户和模型都不能指定 actor。版本选择和补查原因须持久化，避免排查时只能看到最终文本。

## 5. 对前置阶段的要求

第一阶段只需提供最小单产品读取、已存证据 last_checked_at、scope_complete、技术/知识缺口与冲突引用、规则版本及引用闭包，详见第一阶段第3.4节。本阶段基于这些字段实现简报需要的充分度投影和 freshness-policy@1；完整 ProductResearchContext 不要求首期提前实现，不从报告正文重建事实。

不要求第一阶段提前建简报表/工具/队列或实现 freshness 消费策略。阶段二只需保持专题事实和假设可分离、版本固定；简报不能修改专题评级。

## 6. 验收与交付边界

测试覆盖：仅企业输入、岗位/产品定向、未知人员、旧技能不当成现任部署、缺档案只创建一次研究、相同请求重放、跟随他人研究不追加任务、过期资料不被生成时间洗新、研究失败仍给真实限制、取消不取消共享任务、重启不重发，以及纯读取零模型/零上游调用。

实际 HTTP MCP＋SQLite 验证任务与引用，真实图谱通过远程 native gate；简报提问使用固定合成场景核验非诱导性。真实上游及真实宿主另记 tested SHA 和环境，不用合成成功替代。无新网页、构建仍仅远程。
