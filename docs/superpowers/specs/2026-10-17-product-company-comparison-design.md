# 单产品企业比较：功能设计与接口衔接

日期：2026-10-17。状态：设计方案，未实施。前置为持续研究、产品销售场景专题、首次拜访准备；实施顺序不变。

参考：[第一阶段方案](../plans/2026-10-17-continuous-company-research.md)、[专题设计](2026-10-17-product-sales-scenario-design.md)、[首次拜访准备](2026-10-17-first-visit-preparation-design.md)。本文件固定产品行为与排序语义，具体代码任务在前置阶段验收后拆分。

## 1. 输入、目标与范围

输入一款现有 ProductKey 和明确企业列表，首版2–10家。列表项为 credit_code 或 dossier_id，不接受模糊公司名直接排序；同企业的两个标识解析后重复则报参数错误。信用代码已明确但没有研究档案时可进入补研清单，不要求为比较预先创建档案。

给出拜访优先级，另列补研企业。只读取已有资料，不自动调用研究、搜索、CRM或模型。排序和解释用确定性规则与模板，避免同一版本因模型输出漂移。未来用户另行选企业补研，再创建新的比较结果。

产品机会是主要依据。联系人数量、CRM Owner、是否容易联系、岗位覆盖均不参与排序或破同分。竞品使用只按已有证据含义处理，不能单独提升替换机会。无百分制评分、成交概率或跨七产品综合分。

## 2. 版本固定与可比性门槛

请求接受时固定 assessed_at 和当前业务 SQLite 可读快照，为每企业解析该产品最后覆盖它的研究版本。一个公司多个产品版本不能被最新无关产品覆盖。读取不到版本/不兼容版本时列补研，不隐式回退到更早的有利结论。

读取相同版本但不同 assessed_at 时，时效判定可能不同；结果保存 assessed_at、freshness_policy_version、ranking_policy_version、evaluator_version，重读历史比较不重新计算。新比较可以解释资料或时间变化导致的结果差异。

企业进入排序必须满足：

- 有目标产品覆盖，引用闭包完整，核心场景有确认归属的事实依据。
- product level 为高/中/低，confidence 有已知值；待核实单列补研，不强行放在末位。
- 无会影响该产品判断的未处理技术缺口、重大归属/事实冲突。
- 决定排序的依据可按 freshness-policy@1 使用：动态线索复查周期30天，基础场景180天。未知日期不能支持近期时机；若仍有足够新鲜的核心场景，可在不计该时机的情况下排序。
- 同一批排序使用相同 evaluator_version 和可比较规则。首版要求当前部署支持的同一版本；旧评级规则版本列补研，不在只读比较中重新计算或写入。

partial 研究不一律排除：只要本产品覆盖完整、缺口属于别的产品，可参与。completed 研究也不自动等于资料充分。“低”若有完整充分依据，应作为真实低机会参与；资料不足则进入补研，两者严格区分。

已通过门槛的企业缺少联系方式或人员资料不影响资格。没有符合条件的企业时返回空排名和补研清单，不能硬挑前三。

## 3. 排序规则 ranking-policy@1

仅在通过可比性门槛的企业之间依次比较以下项；方向和逻辑固定，不使用权重模型：

1. 产品机会等级：高 → 中 → 低，严格复用已存规则结果。
2. 证据置信度：高 → 中 → 低。
3. 有效时机：明确且仍有效的相关采购/建设动作 → 有依据的相关项目/需求变化 → 未确认有效时机。
4. 已确认且仍适用的明确阻碍：没有已记录的明确阻碍优先于存在明确阻碍；这只是已知记录情况，不宣称完全没有阻碍。

时机由结构化 timing_signals 经代码校验后归类，不由摘要关键词决定。采购需产品范围匹配、主体确认、发布时间有效、没有结束/取消反证；采购90天、其他365天边界沿既有机会规则。复查周期30天用于检查记录是否仍适用，不替代事件发生时间。招聘要求可作为已有关联场景的信号，但不能被提升为明确采购。

工程场景匹配体现在进入门槛和既有产品机会规则中，不再重复加分。重复来源、字段数量、报告长度、软件品牌数量不作排序项。明确阻碍已经影响等级时仍只作为同级条件显示，不再对等级二次扣分。

四项相同为同一优先级，使用 dense rank（1、1、2）；同级内部按 credit_code 稳定展示，明确这是展示顺序而非推荐差异。contact_conditions 不参与比较器，单独变更联系人资料不能改变 rank。

用户解释逐企业给出等级/置信度、场景与时机依据、已知阻碍、关键不确定性。优先级不是对真实客户价值的全局判断，只针对指定产品和本批已知资料。

## 4. 输出、联系人条件与差异

结果分两区：

- 可比企业：rank、企业、目标产品、机会/置信度、排序依据、相关证据、时间、研究版本及独立的联系条件。
- 补研企业：missing_research/product_not_covered/stale_core_evidence/insufficient_scene/unresolved_conflict/technical_gap/incompatible_method 等固定原因、对应 gap_ids 和建议研究问题，不给低价值标签或虚构排名。

联系条件仅读取已有共享图谱，最多每企业5人，展示相关岗位、任职状态、资料时间和是否截断。全比较图谱读取最多40次，单企业最多4次，按 credit_code 稳定遍历；失败/超量为 unknown/partial，不改变排名。无直接联系方式，不联网查CRM；图谱未启用仍可比较。保存所采用的联系人快照和实体/关系版本，历史重读不取实时数据。

证据使用本次固定的研究版本定位；不同企业 evidence_id 相同仍以 (version_id,evidence_id) 作为引用。读取失败时返回明确失败，不能串到另一企业。新增比较可传 previous_comparison_id；要求同产品及同企业集合，输出资格变化、研究版本/证据变化、排序变化及规则/时间变化，不能把纯联系人更新当成机会变化。

## 5. MCP 与存储

| MCP 工具 | 参数与行为 |
| --- | --- |
| compare_company_opportunities | product、companies（2–10）、operation_id、可选 previous_comparison_id；返回 comparison_id/status，不触发补研 |
| get_company_comparison | comparison_id；返回保存的排名/补研清单/独立联系条件及版本；读取不刷新 |
| get_company_comparison_evidence | comparison_id、credit_code、可选 claim_id、offset=0、limit=10（1–20）；验证企业属于比较后读取固定版本证据 |

新增 company_comparisons：comparison_id、actor、operation_id、request_hash、request_json、assessed_at、input_refs_json、status、result_json、error_code、created_at/finished_at。UNIQUE(actor,operation_id)。结果最大2MiB；证据通过固定版本引用，不复制完整研究快照。首版不删除研究版本，因此引用可回读；未来版本删除功能必须另行设计引用保留，不能悄悄断链。

同一 operation_id 同请求回放原 comparison_id，不同请求冲突。状态 queued/running/completed/partial/failed；比较工作并发1、最多20待执行，每用户活跃最多3，单任务30秒硬期限，不使用研究上游预算。默认有补研企业不意味着系统部分失败，completed 可以带补研清单；图谱读取等技术缺口标 partial。企业版本读取失败转补研技术缺口，整体数据库/持久化失败为 failed。重启未完成任务标失败，不自动生成新比较。

共享读取和创建，actor 从认证取值。没有自动通知或新 UI；纯排名文本由确定性模板生成，不引入模型不稳定性。

## 6. 前置接口与验收

第一阶段提供最小单产品读取、产品覆盖与缺口、evaluator_version、已验证claims/产品机会、证据时间及其依赖引用。本比较阶段实现跨企业固定版本批量读取和timing_signals/known_blockers专用投影，基于真实消费者需要定义完整ProductResearchContext；不要求第一阶段提前交付这些投影或批量API。复用拜访阶段已有freshness策略，不重复实现。消费者不得从中文报告倒推字段，不修改旧评级规则。

本阶段生成的 timing_signals/known_blockers 无证据时为空并带 knowledge_gaps，不能伪造“无阻碍”。专题路径是假设，不能直接填 timing_signals；只有经过第一阶段事实校验的新增证据才可参与。

验收：高/中/低排序、待核实不降为低、有效/结束/未来/未知日期信号、部分覆盖、旧规则不混排、同级并列、名字相似不合并、重复企业拒绝、无研究只列补研、联系人变多排名不变、只读路径零上游/零模型、版本变更不污染旧结果、所有不足场景不强行排名。

使用相同版本、assessed_at 和 policy 反复运行必须完全一致；联系人快照变更仅改变独立展示。实际 HTTP MCP＋真实 SQLite 和远程原生图谱分别验证，旧产品规则回归不变。真实客户判断与宿主可用性另行验收，构建仅远程。
