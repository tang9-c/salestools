# 企业资料与联系人图谱互通设计

日期：2026-10-12

状态：聊天中的设计范围已确认；本文待用户审阅，尚未进入实施。

## 1. 目标与范围

一次交付可靠主体关联与六个入口互通：联系人搜索、图谱组织详情、企业画像、企业问答、联系人问答和历史报告。

采用精简方案：增加组织与企业的关联记录、一个内部共享查询服务，在已有工具和界面中接入。继续使用现有企业画像、评估数据库及联系人图谱，不迁移全部数据，不复制报告进组织节点。

本次不建设独立统一主体库、全局证据库、通用冲突引擎、网页版本系统、变化通知、补查材料持久化或新的聚合缓存。保留既有工具的公开调查能力；浏览已有资料不触发外部调查或正式评估。

## 2. 现有基础

- 企业画像和评估记录在 Node 侧 SQLite 中，以信用代码定位企业。
- Organization、Person、Project 和关系由独立图谱进程保存；Organization 已有 identifier 字段。
- ask_company 使用企业画像和评估证据快照；ask_contacts 使用图谱关系与引文校验，两者尚未互通。
- search_contacts 的 App 通过 get_contact 分页读取关系和证据。
- get_assessment_report 已根据存储报告生成展示结果；本次不改写存储报告，也不移除既有的新鲜度提示。

## 3. 主体关联

### 3.1 标识与存储

使用 Organization.entity_id 与企业 credit_code 建立关联，不再引入第三套主体 ID。一家企业可关联多个组织节点，一个组织同一时刻最多关联一家企业；不自动合并节点。

在现有 SQLite 中增加关联存储，记录组织 ID、信用代码、确认或撤销状态、关联依据、操作者、版本、时间，以及建立关联时的组织身份字段摘要。仅名称、法定名称、标识符构成身份摘要，联系方式变化不触发身份冲突。

写操作复用项目的 operation_id、版本检查和审计模式。关联变更保留可追溯的操作记录，无需扩展为通用事件系统。

### 3.2 读取时的关联判定

对外使用 unlinked、candidate、confirmed、conflict、revoked 五种状态：

1. 优先读取显式关联；已撤销记录阻止自动重新关联，直到用户重新确认。
2. 已确认关联的组织身份字段变化、节点归档或代码冲突时，不继续聚合原企业资料；返回冲突或未找到原因。
3. 没有显式记录时，有来源证据的统一社会信用代码通过格式及校验位检查、与已有画像代码一致、组织名称匹配法定名称或画像中已有依据的曾用名，且无冲突，可在读取结果中判为 confirmed，标记 basis=identifier_match。
4. 上述自动判定是只读计算，不在搜索过程中写入关联表，也不调用外部企业查询。
5. 只有名称时，从已有画像生成候选；即使唯一同名也不自动确认。使用既有名称规范化逻辑，不依赖模型猜测身份。
6. 没有代码的学校等组织保持原有档案和关系能力。没有可确认的企业主体时，不附加企业报告。

显式人工关联和只读自动关联都须在正向详情及反向企业查询中生效。反向查询使用精确标识符/名称过滤和批量查询；如需补充图谱查询操作，只增加此目的所需的最小能力，禁止逐次扫描整个联系人库。

### 3.3 link_company

新增聊天可调用工具 link_company，支持 confirm 和 unlink：

- 两种操作都要求 organization_id、operation_id、expected_organization_version、expected_link_version；不存在显式记录时关联版本为 0。
- confirm 还要求 credit_code 和非空审核说明；目标必须是已有企业画像，组织必须存在且未归档。存在不同代码的有效标识符时拒绝确认，需先纠正原数据。
- 名称候选可经人工说明确认。替换已有目标也属于 confirm，必须提供当前关联版本并留下原关联记录。
- unlink 写入撤销状态，包括撤销当前只读自动匹配；避免下一次读取又自动关联。
- 操作者来自鉴权上下文，不允许调用者伪造。相同操作 ID 和参数重试返回原结果；参数变化拒绝。
- 不把图谱和 SQLite 当作一个跨库事务：写前检查图谱版本，读取时重新验证身份摘要。并发身份变更造成的失效必须显示 conflict，不能持续输出错误关联。

## 4. 共享查询服务

在 Node 层增加一个服务，依赖现有画像、评估仓储及图谱访问接口。MCP 工具调用内部服务，不互相调用 MCP 工具。

服务只承担四类读取：组织关联和摘要、企业关联人物与项目、分页报告目录、问答所需材料。内部可以拆成小函数，不建立插件框架或通用查询语言。

### 4.1 汇总规则

- 只有 confirmed 关联可用于跨库统计、报告展示和事实回答。候选只展示匹配状态与候选身份，不能展示为该节点已有报告。
- 报告数量指已完成且调用者可读的报告条数，最新报告按 completed_at、assessment_id 确定顺序；过期报告仍可浏览，须展示时间，不能标成最新事实。
- 企业关联人物包括任职/机构关联及有证据的项目参与路径；项目包括直接关联该组织的项目和通过 clientOrganization 服务该组织的项目。
- 项目客户与雇主分开表示。组织员工参与了某项目，不足以证明该项目属于该企业；不将这种路径计入企业项目数量。
- 人物与项目按实体 ID 去重；关系按关系 ID 去重。不同 ID 的重复档案不自动合并，数量标明是库内去重节点数。
- 不将家庭关系或联系方式加入企业概览和跨库问答材料。
- 已有完整计数能力可返回精确数量；只取得部分分页时返回 count=null、loaded_count 和 complete=false，不用已加载数量冒充总数。

### 4.2 证据与时间

直接复用已有 evidence_id、文件哈希、来源 URL、报告快照证据 ID 和时间字段。内部使用来源类型与原记录 ID 组成引用键，不新建全局证据存储。

重复文件按哈希识别；不同事实仍保留，但同一文件多次导入不成为多个独立来源。网页引用复用现有去重规则；同一 URL 的冲突内容不静默覆盖。报告结论注明是历史分析，不把报告及其引用材料重复算为独立佐证。

任职状态沿用现有 current、historical、unknown 等实际记录语义，不从无结束日期或最近采集时间推断现任。已过期画像可供历史展示，但不能绕过 ask_company 现有主体画像有效性要求。

保留既有证据校验。明显矛盾或原记录已标记冲突时，回答说明无法确认；不新增自动裁决冲突的模型或规则系统。

### 4.3 权限与故障

沿用实际已有的鉴权与可见范围，不假设项目已实现租户级权限。企业资料互通不能暴露导入者专属的候选预览、原始文件或任务材料；企业概览只读取正式档案及可访问的来源。

附加资料统一返回读取状态和 warnings：ok、partial、unavailable、not_applicable。没有记录与读取失败须可区分；失败或未完成时相关计数为 null。

图谱关闭、单源失败或查询预算耗尽，不破坏基础搜索/画像/报告结果。问答材料不足沿用 insufficient；不得用失败代替否定事实。没有新增持久化聚合缓存，仅允许单次请求内去重和复用读取。

## 5. 工具与界面变化

所有原必填参数、搜索排序和分页语义保留。同步调整服务、输出 Schema、工具说明及文档，新增字段不得被现有严格 Schema 丢弃或拒绝。

| 入口 | 扩展行为 |
| --- | --- |
| search_contacts | Organization 命中项增加 company_context：关联状态、画像存在性、已完成报告数量、最新报告完成时间和读取状态。批量查画像与报告，不对每个结果独立读全文；Person/Project 命中不附加无关公司资料。 |
| get_contact / 图谱节点详情 | 增加可选 include_company_context，默认 false；组织节点被点击时开启。返回基础画像、latest_report 摘要及可分页历史目录。报告目录独立使用 report_offset/report_limit（默认 10，上限 50），返回 next_offset。关系和证据保留各自分页；图谱补齐节点名称时不开启完整公司详情。 |
| get_company_profile | 对实际确定的唯一企业主体补充 organization_ids、人物/项目数量及报告摘要。多主体候选分别保留，不跨候选合并统计。 |
| ask_company | 使用共享服务选取与问题相关的职业关系、项目及既有评估证据。继续保持当前公开补查范围和预算，不自动启动完整评估；跨库资料不绕过原主体校验。 |
| ask_contacts | 涉及企业身份或业务背景时，在已确认关联上补充画像或报告证据。仅询问姓名、就读等与公司背景无关的问题，不额外读取报告。 |
| get_assessment_report | 增加 generated_at（存储 completed_at）。可选 include_related_updates 默认 false；开启时返回与报告正文分离的 related_updates。 |

latest_report 只包含 assessment_id、完成/采集时间、既有机会等级与推荐产品，不在搜索时生成新的模型摘要。完整报告通过已有 get_assessment_report 按 ID 读取。

图谱详情提供关联状态、画像、现有职业关系、最新报告摘要及分页历史入口。点击报告调用 get_assessment_report；不增加备用普通网页查询地址。查看完整报告的工具需要对 App 开放，沿用服务端鉴权。App 不支持时同一资料仍可通过聊天工具读取。

related_updates 只表示已保存资料中，在报告完成后采集或更新的相关记录，不声称其事实发生于报告之后，也不声称已完成全量差异分析。首版限制 20 条，按记录时间倒序返回，注明范围、截断及不可用来源；没有可靠时间依据的记录不纳入。不得为此抓取外部新资料。

## 6. 问答引用与读取预算

保留两个问答工具现有返回字段和引用契约；新增 context_citations 承载跨库引用，避免将文件证据伪装成网页来源。

每条 context_citation 包含可区分来源的 ref、来源类型、主体标识、短引文或已保存的字段值，以及可用的原 evidence_id、entity_id、relation_id、assessment_id、URL、页码和时间。只填实际存在的定位信息，不生成虚构引文。正文引用使用这些 ref，并在服务端校验其确实属于本次提供给模型的材料。

ask_contacts 原 facts/citations 校验继续生效；context_citations 独立校验。企业背景引用不能替代人物关系证据，也不能证明某人负责企业采购。

问答首版最多补充 20 条跨库材料、读取 12 个相关图谱档案及最新一个已完成报告的快照；优先使用明确主体、职业关系和问题相关证据。用户显式指定的 assessment_id 仍优先使用并核对主体。预算沿用模型总输入字节限制，超限明确标注遗漏，不无上限递归扩图。

## 7. 交付与验证

实施顺序：关联存储和查询 → 共享读取与证据适配 → 搜索、画像和图谱详情 → 两个问答及报告扩展 → 整体验收。作为同一版本交付，不要求一次合并全部实现代码。

必须覆盖的验收场景：

1. 有证据信用代码及一致名称正确关联；唯一同名但无码仍为候选；学校无代码正常工作。
2. 显式确认、替换、解除、重复重试及版本冲突按预期处理；解除后自动匹配不重新生效。
3. 多个组织节点对应同一企业时，正反向查询一致；身份变化或归档停止错误聚合。
4. 六个入口读取相同主体资料；图谱历史报告可翻页并打开全文；搜索排序和关系分页不变。
5. 重复文件不算多个独立来源，unknown 任职不被写成现任，项目客户不被当作雇主。
6. 公司背景与人物关系分别引用，伪造引用被拒绝，超出读取预算明确说明。
7. 部分数据源不可用时保留基础结果；未知计数不返回 0；原始导入预览和文件不经互通泄露。
8. 原报告存储正文不变，生成时间准确，后续资料独立展示且时间含义明确。

遵守禁止本地构建约束；本地仅执行不产出构建物的类型、语法、diff 检查和适用解释器测试。构建、native/full-suite、页面 bundle 与真实容器 gate 使用远程 CI，并沿用联系人上传验证的只读、合成资料和非生产环境边界。

图谱 App 在真实宿主验收时记录客户端/环境版本、tested SHA、实际结果与脱敏证据。模拟浏览器结果不代替 Codex 或 ChatGPT 宿主验收。
