# 真实企业报告质量修复设计

## 背景与已复现现象

2026-09-02 使用当前 `main`、临时内存 SQLite 和本地 HTTP MCP，对已确认主体“深圳市正浩创新科技股份有限公司”（统一社会信用代码 `91440300MA5EL4TP31`）执行了一次真实企查查、豆包搜索和方舟评估。任务在 175 秒内完成，但报告质量未通过验收：

- QCC 为 `partial`，8 次 attempt 中 6 次成功、2 次失败；
- 豆包搜索 8/8 成功，方舟 1/1 成功；
- 273 条原始证据中入选 10 条，完整方舟请求为 12,126 bytes；
- 报告具有完整七产品结构，但行业为 `unverified`、综合机会为“待核实”、推荐产品为空；
- Markdown 没有直接链接，“来源链接不可用”出现 394 次。

诊断只记录字段形状、计数、类型化错误和派生结果，不保存 QCC 原始响应、网页正文、凭据或完整方舟输出。

## 已确认根因

### 1. QCC 调用与真实契约不一致

- `get_financing_records` 调用成功，但真实中文结构为 `股权融资.创投融资[]`；旧 mapper 只接受 `融资信息[]`，因此产生 `INVALID_RESPONSE`。
- `get_annual_reports` 存在于 QCC 数据目录和实时 `qcc-company` 工具目录，但当前代码错误地将它路由到 `qcc-operation`，上游返回 `REMOTE_PROTOCOL_ERROR`。
- 真实中文年报根结构为 `企业年报信息[]`，包含 `年报年度`、`发布日期`、`企业基本信息`、`企业资产状况信息`、`社保信息`等；旧 mapper 没有中文年报契约。
- `get_qualifications` 存在于实时 `qcc-operation`，真实中文根结构为 `资质证书信息[]`；旧 mapper 只有标准英文结构，没有中文资质契约。
- `get_recruitment_info` 本次真实映射成功 30 条，全部没有上游直接 URL，不是失败项。

### 2. QCC-first 装载饿死豆包直链

`selectItems` 把全部 QCC 候选排在全部豆包候选之前。四类预留之后的填充继续采用这个顺序；大量体积较小的 QCC 招聘和专利条目会耗尽剩余请求预算，导致有真实 URL 的豆包证据不能进入方舟。

真实差分实验只调用豆包搜索和方舟：80 条搜索结果中 72 条主体确认，最终 8 条入选证据全部带 URL 且主体确认。该结果证明豆包 mapper 没有丢 URL，问题发生在混合证据装载层。

### 3. 逐条链接 gap 被双重渲染

QCC mapper 为每条没有直接 URL 的证据生成 `企查查来源链接不可用：<evidence_id>`。报告模型把所有 gap 同时用于：

- 分层缺口区；
- `nextVerificationActions`。

因此约 197 条逐条链接 gap 被显示两遍，形成 394 次“来源链接不可用”。

### 4. 行业事实与 P1/P2 标签之间缺少确定性映射

真实搜索-only 差分实验中，方舟已从主体确认且带 URL 的证据抽取两条 direct 事实，其中包含行业事实，但行业分类仍为 `unverified`。公开产品证据明确包含“移动储能、清洁能源、便携式电源、太阳能技术、智能家居能源解决方案”等词。当前提示只列出 P1/P2 大类，没有定义事实词到行业标签的确定性映射，模型按保守规则拒绝分类。

当前机会规则又把 `industryClassification === 'unverified'` 当作所有产品的全局门槛，使行业标签错误地覆盖更直接的产品、招聘和采购证据。

## 设计原则

- 行业分类只是标签和辅助信号，不能约束或否决产品机会。
- 主体归属和证据强度仍是硬约束；不能为了得到 P1/P2 而放宽证据可信度。
- QCC、豆包和方舟继续是受信任数据源，但真实响应仍必须通过严格运行时 Schema。
- 只修已复现的四条链路，不增加服务、数据库表、缓存层、通用规则平台或新的公开配置。
- 保持单进程、SQLite、轻量队列、总调用预算和 12,288-byte 方舟完整请求上限不变。

## 设计

### 1. QCC 路由与中文契约

`qcc-company` allowlist 加入 `get_annual_reports`，`qcc-operation` 删除该工具。正式评估中的年报调用改用 `server: 'company'`。

融资中文 mapper 接受以下真实结构：

```text
股权融资
└── 创投融资[]
    ├── 融资日期
    ├── 融资轮次
    ├── 融资金额
    ├── 投资方[]
    ├── 关联机构[]
    ├── 交易股权
    ├── 企业估值
    └── 来源
```

输出继续使用现有统一字段：`Date`、`Round`、`Amount`、`Investors`、`Url`。`投资方`作为投资方主字段；只有它为空时才使用`关联机构`补充。`来源`只有通过现有 HTTP(S) URL 校验时才成为证据 URL。

年报中文 mapper 接受 `企业年报信息[]`。每个年报只派生：

- 年报年度；
- 发布日期；
- 从业人数；
- 企业经营状态；
- 资产总额；
- 营业总收入；
- 主营业务收入。

这些字段来自正式年报披露，不进行估算。公开值为空、非数字或未披露时保留为空。年报网页/网店地址不冒充年报直接来源 URL。

资质中文 mapper 接受 `资质证书信息[]`，只派生资质名称、类别与等级、证书编号、发证日期、有效期至、产品名称和证书状态。没有上游直接记录 URL 时保持 `null`。

未知根结构、关键数组类型错误或记录缺少最小识别字段时继续抛出类型化 `INVALID_RESPONSE`/`UNMAPPABLE_DATASET`，来源降级为 `partial`，不得用递归遍历猜测字段语义。

### 2. 有界的来源多样性预留

现有两阶段 16-mask 类别覆盖算法保持不变。类别预留完成后、普通候选填充前，增加一个来源多样性步骤：

1. 从豆包候选中筛选 `url !== null` 且 `entityMatch` 为 `confirmed` 或 `probable` 的证据；
2. 若当前预留集合尚无此类豆包证据，按稳定顺序尝试加入一条；
3. 优先级依次为 `official_products`、`engineering`、`software_ecosystem`、`recruitment`、`quality`、`procurement`、`expansion_financing`；
4. 仍使用完整序列化请求字节测量和既有内容缩减逻辑；放不下时不删除已经预留的类别；
5. 随后继续现有无固定条数的候选填充。

这一步只保证“有合格且可容纳时至少送入一条直链搜索证据”，不保证模型必须引用它，也不伪造报告链接。

### 3. 确定性行业标签

新增纯函数行业分类器，输入为方舟验证后的 `EvidenceBundle`，输出更新后的 `industryClassification` 和 `industryEvidenceIds`。它只在方舟结果为 `unverified` 时尝试补充分类；方舟已经给出 P1/P2/non_target 时保持原结果。

可参与分类的事实必须同时满足：

- `kind` 为 `industry`、`product_scene` 或 `manufacturing`；
- `strength` 为 `direct` 或 `supporting`；
- `entityScope === 'legal_entity'`；
- `entityMatch === 'confirmed'`；
- 至少引用一条存在于 `evidence` 的证据；
- 每条被引用证据同样属于确认法定主体。

v0.1 只维护与既有目标行业对应的明确关键词集合。首个必须覆盖的可复用 P1 规则为：

- 新能源装备：`移动储能`、`便携式电源`、`便携储能`、`家庭储能`、`储能设备`、`储能系统`、`光伏逆变器`、`太阳能逆变器`、`清洁能源设备`。

后续 P1/P2 词表必须直接对应已批准行业列表，不使用企业名称、品牌名称或信用代码。命中多个同等级行业仍返回对应 P1/P2；同时命中 P1 与 P2、只有弱/未确认事实或没有明确词时保持 `unverified`。分类使用命中事实的 evidence IDs 作为行业证据链。

行业标签对机会规则的作用限定为：

- 可以成为辅助理由或同等级稳定排序信号；
- 不能单独把产品提升到“中”或“高”；
- `unverified` 和 `non_target` 不能强制产品变为“待核实”或“低”；
- 产品等级继续由产品场景、招聘、软件生态、工程方法、采购、主体归属和证据强度决定。

因此删除 `industryClassification === 'unverified'` 这一产品全局门槛。主体冲突、所有正向证据均为弱证据或未确认主体等现有可信度门槛保持不变。

### 4. 缺口聚合与销售动作

报告模型在展示层识别 `QCC_UNAVAILABLE_LINK_AUDIT_GAP_PREFIX`：

- 从逐条显示列表中移除这些内部 gap；
- 如果数量大于零，追加一条聚合审计 gap：`企查查有 N 条证据未提供直接来源链接`；
- EvidenceBundle 中的原始逐条 gap 仍保留，用于证据级审计协议，不写入新的数据库字段。

`nextVerificationActions` 只由 `rating` 和 `enhancement` gap 生成。`audit` gap 只出现在审计缺口区，不再重复生成“核实……”动作。事实行仍按自身 `EvidenceReference.url` 决定渲染真实链接或“来源链接不可用”。

## 数据流

```text
真实 QCC Server
  -> 严格中文/标准契约 mapper
  -> QCC ResearchItem + 证据级链接 gap

真实豆包搜索
  -> URL/主体归属 mapper
  -> Search ResearchItem

ResearchBundle
  -> 四类最大覆盖
  -> 合格豆包直链来源预留
  -> 其余证据填充
  -> 方舟事实抽取
  -> 证据来源校验
  -> 确定性行业标签补充
  -> 产品机会规则（行业非门槛）
  -> gap 展示聚合
  -> Markdown
```

## 测试与验收

### 自动化测试

- QCC 真实脱敏结构夹具：嵌套融资、中文年报、中文资质；先证明旧 mapper RED，再实现 GREEN。
- 路由测试：`get_annual_reports` 必须调用 `company`，且 operation allowlist 拒绝该工具。
- 装载压力测试：大量 QCC 条目与合格豆包直链并存时，最终至少保留一条豆包证据；四类最大覆盖、稳定顺序、12,288-byte 上限和无固定条数仍成立。
- 行业分类测试：确认主体的移动储能/便携式电源事实得到 P1；弱事实、未确认主体、无关键词和 P1/P2 冲突保持 `unverified`。
- 机会测试：相同产品证据在 P1、P2、non_target、unverified 四种标签下不会因标签单独改变产品机会等级；行业标签不能独立产生“中/高”。
- 报告测试：数百条逐项 QCC 无链接 gap 只形成一条计数摘要；audit gap 不生成销售动作；真实 URL 仍正常渲染。
- 全量现有测试、typecheck、build 和 diff-check 全部通过。

### 真实端到端复验

对已授权主体“深圳市正浩创新科技股份有限公司”只提交一次 `force_refresh=true` 的新评估，使用临时 SQLite。记录：

- 每个 QCC 工具的安全状态和错误码；
- QCC、豆包和方舟最终来源状态；
- 原始/入选/排除证据数及四类覆盖；
- 入选豆包直链数量；
- 行业标签、行业 evidence IDs 与证据主体归属；
- 七产品机会和推荐产品；
- 报告直接链接数量、聚合链接 gap 数量和总长度；
- 完整方舟请求字节数与总耗时。

验收不要求必须推荐产品，也不要求行业必须为 P1；要求每个结论与证据一致、行业标签不约束产品机会、失败来源准确标注、报告不重复海量审计缺口。真实复验只证明技术和报告契约，不证明销售准确率、SLA 或生产 HTTPS 部署。

## 明确不做

- 不新增分数制、星级、置信度模型或行业规则管理后台。
- 不把行业标签恢复为产品机会硬门槛。
- 不要求报告为了链接覆盖而引用无关搜索结果。
- 不保存真实上游原始响应、网页正文或方舟原始输出。
- 不提高调用预算、不增加并发、不改变 SQLite 缓存期限。
