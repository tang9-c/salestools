# Ark 分批证据提炼设计

日期：2026-09-06

## 目标

修复单次 Ark 请求受 12,288 字节上限约束时，大量已采集证据在进入事实提炼前被永久排除的问题。单次请求上限继续保留；系统改为按字节分批处理，并在本地确定性合并结果。

本次同时修复“非结构化材料已交给 Ark 处理，但报告仍显示待模型整理”的状态错误。不处理爱企查正文抓取、简称归属和专利详情，它们是后续独立问题。

## 约束

- 不取消 `ARK_REQUEST_MAX_BYTES`，每个完整 Ark HTTP 请求仍必须在该上限内。
- 不把所有证据拼入一个更大的请求，不依赖网关扩容。
- 不新增独立 Worker、消息队列、数据库表或最终合并模型调用。
- 不保存上游原始响应。
- MCP 四个工具及 `get_assessment_report` 顶层字段保持不变。
- 机会规则继续只消费验证后的 `EvidenceBundle`。

## 数据流程

```text
QCC + 豆包搜索 ResearchItem
        ↓
确定性预处理：按 evidenceId 去重，同 URL 网页结果保留信息最完整的一条
        ↓
按完整 Ark 请求字节数稳定分批
        ↓
批次 1 ─┐
批次 2 ─┼─ Ark 分别提炼并验证 EvidenceBundle
批次 N ─┘
        ↓
本地确定性合并 evidence / facts / financing / conflicts / gaps
        ↓
现有确定性机会规则与 Markdown 报告
```

## 分批规则

新增配置：

```ini
MAX_ARK_BATCHES=8
```

沿用现有 `ARK_REQUEST_MAX_BYTES` 和“可重试错误最多重试一次”的规则，不增加第二套重试配置。

分批器执行以下步骤：

1. `evidenceId` 相同的条目只保留一条。
2. 豆包搜索结果 URL 规范化后相同的，保留正文、摘要信息量更高的一条；QCC 无 URL 条目不得因此去重。
3. 沿用当前四类覆盖、产品词、招聘/工程方法和有效网页链接优先级。
4. 从剩余条目中生成一个不超过完整请求字节上限的批次，然后移除已选条目并继续生成下一批。
5. 每批至少处理一条。单条证据连同系统提示仍无法容纳时，将该条记为未处理并继续，不能形成死循环。
6. 达到 `MAX_ARK_BATCHES` 后仍有剩余证据时明确记录容量缺口，不得暗示剩余证据不存在。

“代表样本 N/M”改为整个批处理过程的审计结果；正常情况下不再把每个批次内部的临时选样描述写入最终报告。

## Ark 调用与失败处理

- 每个批次独立调用 Ark，并沿用现有可重试错误判定，最多重试一次。
- 一个批次最终失败时标记该批次 `failed`，继续处理其他批次。
- 至少一个批次成功时，任务仍可完成，Ark 来源状态为 `partial`，报告列出失败批次数和未处理证据数。
- 所有批次均失败时，任务失败并提示“模型事实整理不可用”。
- 调用预算仍是硬约束。为避免默认配置让后续批次永远无法执行，`MAX_ARK_CALLS` 默认调整为 16，`MAX_TOTAL_UPSTREAM_CALLS` 默认调整为 32；两者仍可由 `.env` 下调。配置校验要求总预算至少覆盖 QCC、搜索和 Ark 的已配置上限。

## 确定性合并

批次结果按批次顺序合并：

- `evidence`：按 `evidenceId` 去重，来源字段必须与原始 ResearchItem 完全一致。
- `facts`：主体归属、事实类型、产品标签和规范化 statement 全部相同时合并 `evidenceIds`；否则保留为独立事实。
- `financingRecords`：规范化后的摘要、日期、轮次、金额和投资方完全相同时合并 `evidenceIds`；否则分别保留。
- `conflicts`、`gaps`：按规范化文本去重并保持首次出现顺序。
- `industryLabel`：取最早批次中有已确认来源支持的非空标签；后续不同标签写入冲突。行业仍只展示，不参与评分。

每个合并后的结果再次通过 `EvidenceBundleSchema` 和来源追溯校验。不得用本地合并提升主体归属、事实强度或产品标签。

## 非结构化材料状态

`使用非结构化材料，待模型整理` 只属于进入 Ark 前的处理状态，不得无条件复制到最终报告。

- 材料所在批次成功且 Ark 产出引用该 evidence ID 的事实、融资记录或行业标签：移除“待模型整理”。
- 批次成功但没有产出相关事实：改为“模型未从该材料提炼出可采信事实”。
- 批次失败或未执行：标记“材料未完成模型整理”，并附失败或容量原因。

QCC “未提供直接来源链接”仍是独立审计缺口，不受上述状态转换影响。

## 审计与兼容性

在现有 `evidenceSelection` 审计中增加可选字段，以兼容历史报告：

- `batchCount`
- `successfulBatchCount`
- `failedBatchCount`
- `processedCount`
- `unprocessedCount`
- `deduplicatedCount`

`selectedEvidenceIds` 表示所有成功进入 Ark 请求的唯一证据。`researchBytes` 和 `requestBytes` 改为各批次字节数之和。SQLite 继续保存 JSON 审计字段，无需迁移表结构。

普通日志按批次记录 assessment ID、批次序号、条目数、请求字节、尝试次数和结果，不记录证据正文或凭据。

## 测试与验收

必须先写失败测试并观察其因缺少分批能力而失败，再实现代码。

- 92 条测试证据会在最多 8 个批次中稳定装载；所有条目必须明确计入已处理、去重或容量未处理，不再只处理首批 8 条后静默丢弃。
- 每个序列化 Ark 请求均不超过 `ARK_REQUEST_MAX_BYTES`。
- 分批结果稳定；相同输入产生相同批次和合并结果。
- 同 URL 转载结果被确定性去重，QCC 无 URL 记录不会误删。
- 单条过大证据不会造成死循环，并产生明确未处理缺口。
- 单批失败后其他批次继续；部分成功时任务完成且 Ark 为 `partial`。
- 全部批次失败时任务为 `failed`。
- 合并不能提升主体归属或事实强度，冲突行业标签被记录。
- 已成功提炼的非结构化材料不再显示“待模型整理”。
- 未产出事实、批次失败和容量未处理三种情况分别显示准确原因。
- 历史审计 JSON 仍可读取。
- 完整测试、类型检查和构建通过。

真实验收使用一个允许查询的企业，核对：原始证据数、去重数、批次数、成功/失败批次数、处理/未处理数，以及产品证据是否来自全部成功批次。真实调用不作为单元测试替代。

## 明确延期

- 爱企查及其他网页的二次正文抓取。
- 品牌、简称和曾用名的增强归属判断。
- 专利摘要或说明书补充。
- Ark 并发批处理、成本面板和自适应模型选择。
- 修改产品机会规则、综合机会或推荐产品聚合方式。
